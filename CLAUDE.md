# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Data Kiln Works: a local Databricks-style lakehouse (Delta Lake tables on disk, DuckDB as the engine, SQLFrame for the Spark DataFrame API, no JVM). A FastAPI backend plus a single-page Alpine.js UI, with an in-Studio notebook runner (per-user kernels, Databricks-compat shim). There is no JupyterLab server. `README.md` has the full feature catalogue; `FEATURE_COMPARISON.md` maps features to Databricks/Snowflake.

## Running it

Everything runs in Docker. The Python dependencies (`requirements.txt`) are installed in the image, not necessarily on the host.

```bash
docker compose up -d            # build + start everything
docker compose logs -f datakilnworks-studio
docker compose exec datakilnworks-studio python scratch/test_sql_native_inference.py   # run one script
```

| Service | Port | Entry point |
| --- | --- | --- |
| `datakilnworks-studio` | 8891 | `uvicorn web.app:app --reload` |
| `notebook-sandbox` | none (internal `sandbox-net` only) | `uvicorn worker:app --app-dir /opt/sandbox` (code in `sandbox/`) |
| `compute-node-01/02/03` | 8001-8003, compose network only (not published; require `X-Compute-Token`) | `uvicorn web.compute_worker:app` |

- `./web`, `./notebooks`, `./warehouse` and `./docs` are bind-mounted, and the studio uses `--reload`, so edits to `web/*.py` apply without a rebuild. Only `requirements.txt`/`Dockerfile`/`config/00_databricks_shim.py` changes need `docker compose build`. The shim is copied into the image, not mounted.
- Swagger UI is at `/api/docs`; the built-in manual is served from `docs/index.html` at `/docs/`.
- There is no lint config, no pytest setup, and no CI. The tests are standalone scripts in `scratch/` (`test_*.py`, `verify_*.py`). They add the repo root to `sys.path` and are run directly with `python`. Some `verify_*_ui.py` scripts drive the UI.

## Architecture

**Backend (`web/`)**
- `web/app.py` (about 7,300 lines) holds the core FastAPI app and most routes (catalog explorer, ingestion, SQL execution, dashboards, time travel). Feature modules (`warehouses`, `workflow`, `genie`, `copilot`, `lineage`, `onelake`, `mounts`, `volumes`, `autoloader`, `serving`, `mlflow_shim`, `ai_sql`, `dbt_service`, and others) hold logic that `app.py` imports. Some modules define their own routers or route groups, so grep for the route path before assuming where it lives.
- Startup (`startup_event` in `app.py`) initializes the SQLite DBs and launches the background asyncio loops: cron scheduler, alerts, lineage scan, scheduled exports and the Auto Loader daemon. A new background service belongs there.
- Every module resolves `WAREHOUSE_DIR` (env, default `/workspace/warehouse`) on its own. Metadata is stored under `$WAREHOUSE_DIR/.metadata/`, as per-feature SQLite files (`auth.db`, `history.db`, `experiments.db`, `lineage.db`, `autoloader.db`, ...) and JSON files (`sql_warehouses.json`, `catalogs.json`). There is no central config or ORM, so each module owns its schema and its `init_*_db()`.

**Storage / namespace**
- Three-level `catalog.schema.table`. The default catalog's tables live directly at `$WAREHOUSE_DIR/<schema>/<table>` (Delta directories with `_delta_log/`). Additional catalogs live at `$WAREHOUSE_DIR/catalogs/{catalog_id}/`. Table-path resolution is repeated inline in many `app.py` handlers, with a fallback of `WAREHOUSE_DIR/<table>` when there is no schema dir, so keep them consistent when changing it.
- `mounts.py` and `onelake.py` mount external storage (OneLake/Fabric via `azure-storage-file-datalake`, plus others) as catalogs. OneLake paths need the `.Lakehouse` suffix and the `Tables/` prefix. The last several commits were fixes to exactly this.
- Delta reads and writes use `deltalake` (delta-rs) and `duckrun`, and DuckDB attaches catalogs for cross-catalog joins.

**Compute**
- A "SQL warehouse" (`warehouses.py`) is a named T-shirt-sized profile (threads plus `max_memory`, applied to DuckDB as `SET threads` and `SET max_memory`). The three defaults, `wh_starter`, `wh_analytics_pro` and `wh_etl_batch`, map to the `compute-node-0N` containers through the `WH_*_ENDPOINT` env vars. Queries can be forwarded over HTTP to `web/compute_worker.py`, or run in-process.
- `ray_engine.py` optionally scales each warehouse with Ray `DuckDBWorkerActor` pools for scatter-gather scans. It degrades gracefully when Ray isn't installed (`RAY_INSTALLED`).

**Notebooks**
- Notebooks run only through `web/notebook_runner.py` (kernels keyed per `(user, notebook)`; endpoints in `app.py` go through `_notebook_user`: authenticated, `can_access_workspace_path`, and `web/notebook_access.py` for execution). Do not add a shared Jupyter server: it would see every user's folder and the warehouse files. Users a masking policy applies to run in the notebook sandbox instead (`RemoteKernelSession` in `notebook_runner.py` calls `sandbox/worker.py` through `web/sandbox_client.py`; routing is `notebook_access.execution_route`). Sandboxed kernels have no warehouse and read data only through `POST /api/sandbox/sql` (`web/sandbox_gateway.py`, governed like the SQL editor, token bound to the user); the middleware in `app.py` refuses every other route to the sandbox's address, so never add an unauthenticated route that a kernel could reach. `sandbox/shim.py` is the sandbox's IPython startup file. Test: `scratch/test_notebook_sandbox.py` runs against a throwaway sandbox + studio container pair (see its docstring). `config/00_databricks_shim.py` is an IPython startup hook. It injects `spark` (a SQLFrame session sharing the duckrun DuckDB connection), `dbutils`, `display()`, and the `%sql` magic. It also patches `createOrReplaceTempView` so SQLFrame DataFrames are visible to SQL. Notebooks under `notebooks/{Users,Shared}/` are run headless by `notebook_runner.py` (Papermill) and the workflow DAG engine (`workflow.py`).

**Frontend**
- `web/templates/index.html` is a single roughly 27k-line Jinja/Alpine.js file containing every view (Chart.js for charts, Monaco for SQL). Expect large, targeted edits with grep, not whole-file reads. Note the recent fix commits for Alpine expression and scope errors, since inline expressions are brittle.
- The MLflow shim (`mlflow_shim.py`), model serving (`serving.py`) and SQL-native inference functions (`ai_sql.py`, exposing `predict`, `ai_query` and similar as DuckDB UDFs) emulate Databricks MLflow, serving and AI functions locally. LLM backends (LM Studio and Ollama) are configured in `llm_settings.py`.

## Authentication

- `web/auth.py` owns the `users` table (local password auth, PBKDF2). `auth_source` on a user row says who owns the
  password: `local` (default) or an external provider (`ldap`, and later `oidc`/`saml`). `web/auth.py::upsert_external_user`
  is the only way to create/update a non-local account — it writes a random, never-checked password hash, so that account
  can only ever authenticate through its provider's own module.
- `web/ldap_auth.py` is that module for LDAP: real service-account bind, user search (filter-escaped), bind-as-user for the
  password check, group-to-role mapping, and `sync_user`/`sync_all` to re-resolve role/active status against the directory
  later (not just at login). `/api/auth/login` in `app.py` routes to it only when there is no local account yet or the
  existing one is already `auth_source='ldap'`; an existing **local** username is always refused before any LDAP lookup,
  so a login attempt can never take over a local account.
- LDAP `sync_group` (optional group DN) gates login, `discover_and_provision` and `sync_user` alike via `ldap_auth._in_sync_group`; never gate only bulk sync, since login auto-provisions. `user_group` joins `admin_group`/`power_user_group` in `_map_role`; unmatched members get `default_role`.
- `web/oidc_auth.py` is the real OIDC login (auth-code + PKCE; routes `/api/auth/oidc/login|callback` and public `/api/auth/sso` in `app.py`). Attempt state lives in a signed `dkw_oidc` cookie, not server memory. `_provision` refuses any existing username that isn't already `auth_source='oidc'` (and deleted/deactivated ones) — unlike `upsert_external_user`, which would flip `auth_source` and reactivate. `scratch/test_oidc_auth.py` runs against an in-process mock IdP with real RSA/JWKS (not Keycloak/Entra).
- TOTP MFA lives in `web/mfa.py` (RFC 6238 by hand, no pyotp; secret Fernet-encrypted with `.metadata/mfa.key`, backup codes HMAC'd). `/api/auth/login` returns `{mfa_required, mfa_token}` instead of a session when `mfa.is_enabled`; only `/api/auth/login/mfa` turns that into a session (`_session_response`, shared by every password path). **Single-purpose JWTs (MFA step, OIDC state) carry a `purpose` claim and `decode_access_token` rejects any token that has one; the MFA token is also signed with a derived key.** Skipping that once made the mfa_token a valid session (caught by `test_mfa.py`). User getters strip `totp_*` columns via `_public_user`; never `SELECT *` a user into a response. Tests: `scratch/test_mfa.py`, and `scratch/verify_mfa_ui.py` (Playwright, run with `/usr/bin/python3`, against a throwaway container bootstrapped with `INIT_ADMIN_*`).
- `scratch/test_ldap_auth.py` runs against a real `lldap` server on the compose network (see
  `/home/martin/volumes/backendservices`), not a mock; it skips cleanly if lldap is unreachable.
- **No hardcoded accounts.** `init_auth_db()` seeds nothing on its own. `_init_admin_from_env()` (bottom of
  `web/auth.py`) is consulted only when the `users` table is genuinely empty (a brand-new warehouse volume) and reads
  `INIT_ADMIN_USERNAME` / `INIT_ADMIN_PASSWORD_HASH` / `INIT_ADMIN_DISPLAY_NAME`; a missing or malformed
  `INIT_ADMIN_PASSWORD_HASH` is `SystemExit(1)` with a `logger.critical(...)` message (`docker compose build` can't see
  runtime env, so this surfaces as a crash-loop under `restart: unless-stopped`, not a build failure). Generate the
  hash with `python -m web.auth hash-password` (guarded behind `if __name__ == "__main__"` so running it never
  triggers the bootstrap check on itself). An already-seeded warehouse — including the live studio — is never touched
  by this, regardless of what these env vars are set to.
- `must_change_password` on a user row is set whenever someone other than the account holder chose the password (the
  bootstrap admin, or an admin's reset via `reset_user_password(..., chosen_by_self=False)`), and cleared only by a
  successful self-service `change_own_password` (`chosen_by_self=True`). Enforced server-side by the
  `_must_change_password_gate` middleware in `app.py` (403 on every `/api/*` route except
  `login`/`logout`/`me`/`change-password`), not just hidden behind the frontend's forced modal
  (`changePasswordForced` in `index.html`) — a direct API call can't skip it either. That middleware decodes the
  session cookie itself and must replicate `resolve_principal`'s own staleness check (`iat` vs `password_changed_at`);
  skipping that check was a real bug once (a stale, already-invalidated session was misread as the live user).
- The `scratch/test_*.py` throwaway-warehouse tests set `INIT_ADMIN_*` before importing `web.auth`/`web.app`, using a
  fixed precomputed hash for `adminpassword123`; `lead_engineer`/`analyst_bob` are no longer auto-seeded so tests that
  need them call `auth.create_user(...)` explicitly, and clear the bootstrap admin's `must_change_password` with a raw
  `UPDATE users SET must_change_password = 0` (not `reset_user_password`, which also touches `password_changed_at` and
  breaks any test helper that mints a JWT without an `iat` claim). `scratch/` is gitignored (`scratch/test_*.py`,
  `verify_*.py`) and **not** bind-mounted into the container — edits there need `docker cp` before they take effect
  in a running container, unlike `web/`, `notebooks/`, `warehouse/` and `docs/`.

## Governance (tags + column masking + row-level security)

- `web/governance/` holds tags (`tags.py`), masking policies and masks (`policies.py`, `masks.py`, `macros.py`), row filter policies and principal attributes (`row_filters.py`), the query gateway (`enforce.py`, `gateway.py`) and the REST router (`routes.py`). State lives in `warehouse/.metadata/governance.db`.
- **Every code path that runs SQL on behalf of a user must go through the gateway** (`gateway.govern_sql`, `governed_sql_or_raise`, `_gov_or_403` in `app.py`, `masked_relation`, or `mask_arrow` for data Python already holds). Use the *rewritten* SQL for execution and the user's own text for history. Identity comes from `resolve_principal(request)` (never fall back to admin on errors), or `gateway.principal_for_username(owner)` for background work; a missing identity is least privilege.
- `scratch/test_governance_coverage.py` scans `web/*.py` for DuckDB execution sites; a new one must call the gateway or be added to `web/governance/ALLOWLIST.md` with a reason.
- Statements that create tables from tagged columns are followed by `gateway.propagate_tags(...)` (SQL editor, job SQL tasks); do the same in any new path that runs user DML. This also propagates the table-level tag of a row-filtered source an exempt principal read unfiltered.
- Caches of query results must be keyed by `gateway.fingerprint(result)` (the masks *and* row filters the result was computed under; two users under the same policy can resolve to different predicates and must never share a cache entry).
- Row filter policies bind to a tag on a catalog/schema/table (never a column, since a row filter restricts the whole table) and resolve to a literal `WHERE` predicate appended to the same masked subquery masking already builds (`enforce._build_governed_subquery`). Modes: `owner` (a column = the caller's username), `attribute` (a column must be in the caller's assigned `principal_attributes` values, fail-closed when nothing is assigned) and `custom` (a validated boolean expression). Multiple applicable policies on one table combine with AND.
- Tests: `scratch/test_governance_phase{0..6}.py` and `scratch/test_governance_rls_phase{1,2}.py` (run inside the studio container against a throwaway warehouse whose directory is named `warehouse`), `scratch/test_governance_coverage.py` (host), `scratch/verify_governance_ui.py` (Playwright, throwaway instance only, covers both masking and row filter UI).

- **Shallow clone** (`web/table_clone.py`, wired in `app.py` as `_do_shallow_clone`, the REST route and `_execute_clone_statement`, which `execute_sql` calls *before* governance/dispatch because no engine parses the syntax). It **hard-links** the source's data files and writes a fresh version-0 log; do not switch to absolute `add.path` references (delta-rs and DuckDB both resolve them against the clone's root and fail, verified). Governance is part of the contract: `deny_if_subject` first, then the source's *effective* tags are copied to the target **before** the clone exists (fail closed; pruned/rolled back after). Tests: `scratch/test_shallow_clone.py` (engine), `scratch/test_shallow_clone_api.py`, `scratch/verify_clone_ui.py`.

- **Auto-Loader file watching** (`web/autoloader_watch.py`, ctypes inotify, no dependency): a pipeline with `watch_enabled` is woken by `IN_CLOSE_WRITE`/`IN_MOVED_TO` (never `IN_CREATE`: a half-written file would be loaded twice, its fingerprint changes as it grows), debounced by `WatchManager`; the daemon loop only does the low-frequency `watch_sweep_seconds` rescan and calls `sync_watchers()` every tick (which also retries failed watchers). `run_pipeline_cycle` now holds a per-pipeline lock (a second trigger returns `{"skipped": ...}`); the real work is `_run_pipeline_cycle_impl`. Keep `autoloader_watch.is_ignored_name` in step with the discovery filter in the cycle. `scratch/test_autoloader_watch.py` (no daemon: anything ingested was event-triggered) and `scratch/verify_autoloader_watch_ui.py` (throwaway studio, file dropped from the host).

- **Auto-Loader S3 sources** (`web/autoloader_s3.py`, boto3 for listing/copy/delete, DuckDB httpfs for reading in place): a pipeline whose `source_volume_path` starts with `s3://` takes the `_run_s3_cycle` branch; endpoint/credentials come from an S3 mount in `storage_mounts.json` (`source_mount_id`, else bucket match, else first). Identity = key+size+ETag. S3 quarantine copies then deletes best-effort, and `QUARANTINED` hashes are skipped so an undeletable bad object is never retried. Errors that look like access/network (`_looks_like_remote_io_error`) are FAILED, not quarantined. No inotify for S3 (`_validate_source` refuses `watch_enabled`). `boto3` is in requirements.txt, so the image needs `docker compose build`. Tests: `scratch/test_autoloader_s3.py` (in-process moto server; needs `pip install "moto[server]"`, skips without it) and `scratch/verify_autoloader_s3_ui.py`.

- **Container auto-suspend** (`web/warehouse_lifecycle.py` + `web/container_control.py` + `controller/controller.py`): the `auto_stop_mins` setting used to be a flag nobody enforced. Now `autosuspend_loop` (started in `startup_event`) stops/pauses the compute-node container behind an idle warehouse, and `execute_sql` calls `ensure_running` first, which resumes it (per-warehouse lock: concurrent queries share one resume; it also refreshes `last_active_at` so a tick cannot suspend under a query). **The studio must never hold the Docker socket**; only the `container-controller` service does, with an allow-list of compose services (same project), a token and no exec/create/rm. All `sql_warehouses.json` writers take `warehouses._WH_LOCK`. Containers are addressed by compose service = endpoint hostname. Rootless Docker needs `DOCKER_SOCKET_PATH=/run/user/<uid>/docker.sock` (this dev machine is rootless). In a `.env`, values containing `$` (the admin hash) must be single-quoted or Compose mangles them. Test: `scratch/test_container_autosuspend.py`, run on the HOST with `/usr/bin/python3` (builds a throwaway `dkwtest` compose project with real containers; `AUTOSUSPEND_TIME_SCALE=0.05` makes a minute 3 s).

- **dbt uses the duckrun adapter** (`dbt_project/profiles.yml` `type: duckrun`; `duckrun` *is* a dbt adapter on top of dbt-duckdb, so `dbt-core`/`jinja2`/`duckrun` are the dependencies and are listed in `requirements.txt`). `table`/`incremental` models are Delta tables at `<warehouse>/<schema>/<model>` (`root_path` = the warehouse, profile `schema: dbt`); `view` models stay views in `dbt_analytics.duckdb`, which the preview endpoints read (qualified with the profile schema, because a legacy run may have left same-named tables in `main`). **dbt output is closed by default** (`web/dbt_governance.py`, wired into `dbt_service.run_dbt_cli` before/after a data-writing run): the output schemas get the schema-level tag `access=closed` *before* dbt runs (tags inherit downward, so no per-model step and no window), one row policy "dbt output closed by default" (custom filter on a column that never exists, so it fails closed; exempt admin+power_user) denies rows of closed tables, an admin opens a table with a table-level `access=open` (`POST /api/dbt/models/{name}/open`), and after every run source tags are copied onto the outputs via sqlglot column lineage through the whole DAG (tags with source `dbt` are refreshed each run). Side effect worth remembering: any policy applying to a role makes those users "subjects" (`gateway.is_subject`: sandboxed notebooks, no file functions); `DBT_CLOSED_BY_DEFAULT=false` disables it. `dbt run`/previews already `deny_if_subject`. `on-run-start: drop_legacy_duckdb_tables` only matters for a profile that keeps schema `main`; detect legacy tables via `duckdb_tables()`, not dbt's relation type (it reports migrated Delta-backed views as tables). **Config editor and S3 landing** (`web/dbt_config.py`, admin-only endpoints `/api/dbt/config*`): saves are validated (YAML, profile cross-check, `dbt parse` in a scratch copy, plus a hook-macro check because `dbt parse` does NOT render hooks: a hook calling a missing macro passes parse and breaks every run), backed up to `dbt_project/.config_history/` (gitignored) and audited (`DBT_CONFIG_SAVE`, no content). Every S3 mount is exported to every dbt subprocess as `DKW_MOUNT_<ID>_*` env vars (`dbt_config.dbt_env()`: use it for any new dbt subprocess; `USE_SSL` is `True`/`False` because dbt's `as_bool` rejects lowercase); a profile with `root_path: s3://<bucket>` + `storage_options` + a `secrets:` s3 block lands Delta tables at `s3://<bucket>/<schema>/<model>` (verified against moto). `dbt_governance.target()` maps the profile's `root_path` to a catalog (warehouse, or the S3 mount's `catalog_name`; None = outside any catalog: governance is skipped and says so), and everything (closing tag, policy, carry-over, open/close) uses that catalog. **Where the project lives**: `DBT_PROJECT_HOST_DIR` (compose; default `./dbt_project` for dev) is mounted at `/workspace/dbt_project`; in production it is the deployment's *own* repository (the platform repo must not carry a deployment's config). `dbt_service.ensure_project()` (called at startup) seeds an empty directory from `web/dbt_template/` and never overwrites; the config history is app data under `warehouse/.metadata/dbt_config_history` (`DBT_CONFIG_HISTORY_DIR` overrides). The guided settings (`dbt_config.read_settings` / `apply_settings`, `/api/dbt/config/settings*`) are **line-level text edits** (`_locate`/`_set_key`/`_put_block`/`_remove_key`, indentless YAML sequences count as part of their key), never a YAML round-trip, so comments survive; they only propose text, saving is the normal validated PUT. Tests: `scratch/test_dbt_duckrun.py`, `scratch/test_dbt_governance.py`, `scratch/test_dbt_config.py` (needs `pip install "moto[server]"`), `scratch/verify_dbt_config_ui.py` (inside the studio container / throwaway studio, temp dirs only).

- **Git sync of the dbt project** (`web/git_sync.py`, a `Repo` class with two instances: `DBT` and `NOTEBOOKS`; admin-only `/api/git/{status,...}` = dbt and `/api/git/repos/{kind}/...`; panels in the Project files modal and Workspace > Git; branch + pull-request mode is `GIT_MODE=pull_request`, below). Env only: `GIT_REMOTE_URL` (http/https, credentials in the URL are refused), `GIT_TOKEN`, `GIT_BRANCH`. The token reaches git through `GIT_CONFIG_*` env vars (never argv/URL/`.git/config`) and is scrubbed from every message; `GIT_ALLOW_PROTOCOL=http:https`. Every operation refuses unless the project dir is the **top level of its own repo** (in development it sits inside the platform repo; git there would commit the platform). Pull = fast-forward only, refused when dirty, then `dbt parse`, rolled back if dbt rejects it; push never forces; commit is authored as the acting user and refused when a project file has a plaintext credential; build artefacts are excluded through `.git/info/exclude`. `dbt_service.run_dbt_cli` records `git_sha` on each run. **Notebooks** sync only `NOTEBOOKS_DIR/Shared` (env `NOTEBOOKS_GIT_*`, token falls back to `GIT_TOKEN`, audit actions `NB_GIT_*`), never `Users/`; a git *clean filter* (`web/nb_strip.py`, set in the repo's own config and `.git/info/attributes`) strips outputs at commit time so query results never reach the repo, and a pull with an invalid `.ipynb` is rolled back. Tests: `scratch/test_git_sync.py` (dbt and notebooks; in a container on a network with a **throwaway** Gitea, see its docstring) `scratch/verify_git_sync_ui.py` and `scratch/verify_notebook_git_ui.py`. The throwaway studio there is started without `--reload`: restart it after editing `web/`.

- **Editing a history query** (`web/sql_qualify.py`, `POST /api/sql/qualify`, editable working copy in the query-detail modal): the history row is an audit record and is never modified; the user edits a copy and saves it as a saved query. Qualification edits the SQL *text* at sqlglot identifier offsets (`meta.start/end`) so formatting/comments survive, only completes names that resolve to exactly one table (hinted catalog first), skips CTEs, table functions and 3-part names, and reads table names from the catalog directories without opening tables. Test: `scratch/verify_history_edit_ui.py` (throwaway studio, seeded history row). **The history is append-only except for admins**: `DELETE /api/history` (clear all) and `POST /api/history/delete` (selected ids) are `require_role(["admin"])` and each writes `HISTORY_CLEAR`/`HISTORY_DELETE` to `governance_audit` (ids, never SQL); clear-all used to have no role check at all. Test: `scratch/verify_history_delete_ui.py`.

- **Auto-Loader targets** (`web/autoloader.py`): `resolve_target(catalog, schema, table)` returns `(location, storage_options)`; a catalog that is a writable S3 mount lands at `s3://<bucket>/<schema>/<table>` (mount credentials via `mounts.get_s3_storage_options`) and *every* Delta call in `process_single_file`, `_plan_schema_policy`, `_evolve_schema_for_merge` must pass those `storage_options` (use `_is_delta`, not `os.path.exists`, for existence). It raises `TargetError` (a `ValueError`) for unknown, read-only or non-S3 mounts; `create_pipeline`/`update_pipeline` call it so a bad catalog fails at creation. `target_catalogs()` feeds the create dialog's dropdown (`GET /api/autoloader/target-catalogs`); a non-default local catalog now uses its catalog `path` (previously always `WAREHOUSE_DIR/catalogs/<id>`). Source types other than local volumes and `s3://` (sftp, http(s), API) are not implemented. Tests: `scratch/test_autoloader_target.py` (prefer a throwaway **MinIO** container, `TEST_S3_ENDPOINT=host:9000`; delta-rs stalls for minutes against moto's threaded server and botocore rejects underscores in hostnames), `scratch/verify_autoloader_form_ui.py`.

- **Connections and connection sources** (`web/connections.py`, `web/autoloader_conn.py`, admin-only CRUD at `/api/connections*`, Connections modal + a "Connection" source in the create-pipeline dialog): a connection (`http` or `sftp`) holds non-secret config in `connections.db` and its secret Fernet-encrypted (`secrets_store.encrypt_json`, key `.metadata/connections.key`); public views only expose `has_secret`, and update keeps a stored secret when the field is omitted (empty string clears). A pipeline source is `conn://<name>/<relative path>` plus `source_options` JSON (http: `mode` file|api, `records_path`, `params`, `pagination` none|page|offset|next_link; sftp: `recursive`, `settle_seconds`). **Rules to keep**: the path can only extend the connection's base URL/folder (`safe_path`, origin re-checked on every request, redirects and next-links only same-origin, so a stored credential cannot be sent elsewhere); SFTP requires a pinned `host_key_sha256` checked on every connect (Test discovers it; never auto-trust); the remote side is never modified; sources are polled (file events refused). `_run_connection_cycle` stages each new candidate under `.metadata/autoloader_staging/<pipeline>/` and calls `process_single_file(..., identity=(name, hash))`, so the checkpoint identity is the remote's (ETag/Last-Modified/length via HEAD, else content hash; REST = hash of the NDJSON snapshot; sftp = host+path+size+mtime), not the staged copy's. ## Conventions

- Commit messages follow Conventional Commits (`fix(onelake): ...`, `feat(ui): ...`). The working branch is `development`; `main` is the PR target.
- Loggers are named `localspark.*`, a leftover from the project's earlier name. The Docker image is still tagged `localspark-lakehouse-notebook`, and compose references it, so don't rename it casually.

- **Workflow orchestration** (`web/workflow.py`): `validate_job` normalises every job on save (retries 0-10, backoff, timeouts, `run_if`, parameters, triggers, notifications; cycle and undeclared `{{ params.x }}` refusals). Tasks of one run execute **sequentially**. `run_pipeline` handles run_if, retries (`_execute_with_retries`), timeouts (`_run_attempt` interrupts SQL, abandons other work), cancel (`_active` registry), repair (`repair_of`: reuses SUCCESS tasks and the base run's parameters), concurrency (a surplus run is stored as SKIPPED) and notifications (`_notify` through the existing email/slack/webhook modules). **Parameters are injection-guarded** (`_check_param_value`: default pattern, allowed list or owner pattern) because jobs run with the OWNER's rights; never substitute an unchecked value. Triggers: `fire_event` (job chain with depth/loop guard; Auto-Loader hook in `autoloader.run_pipeline_cycle`) and `check_table_triggers` polled by `cron_scheduler_loop` every 15 s (baseline recorded after a run so a job's own writes do not retrigger it). `start_run_in_background` waits until the run row exists (the UI fetches it at once). Runs left RUNNING by a dead process are marked FAILED at scheduler start. New sqlite sites here need `web/governance/ALLOWLIST.md` rows. Tests: `scratch/test_workflow_orchestration.py` (throwaway warehouse, no compose), `scratch/verify_workflow_ui.py`.

- **Streaming ingestion (Kafka / Redpanda)** (`web/streaming.py`, `confluent-kafka` in requirements: image rebuild; `kafka` type in `web/connections.py`; admin/power_user `/api/streams*`, the *Streams* modal in the Auto-Loader view). One runner thread per enabled stream (`sync_runners()` from `streaming_daemon_loop`, started in `startup_event`); `streaming.db` holds `streams`, `stream_state`, `stream_offsets`, `stream_batches`. **Exactly-once**: each Delta commit carries `Transaction("dkw-stream:<id>:<topic>:<partition>", next_offset)`; resume = max(Delta txn, `stream_offsets`); the DLQ table (`<table>_dlq`) is deduplicated by its own `...:dlq` txns, written BEFORE the main table. Never resume from Kafka consumer-group offsets (they are committed only for external lag tools). `build_batch` is pure (schema inference on the first batch, `_rescued_data` for unknown/ill-typed fields, `evolve_schema` adds columns); connection/topic/target of a stream are immutable because the stored offsets belong to them. librdkafka reports *why* a login/TLS failed only in `error_cb`, delivered on `poll()`: `_list_topics_explained` polls after a failed metadata call (without it every auth error reads "broker not reachable"). `import confluent_kafka.admin` explicitly (not pulled in by the package).   **Avro** (`format: avro`): `AvroDecoder` (in `web/streaming.py`) speaks the Confluent wire format, fetches `/schemas/ids/<id>` from the connection's `schema_registry_url` (basic auth via `registry_username` + secret `registry_password`; `allow_redirects=False` so the login never leaves; CA from `ssl_ca_pem` for https) and caches per id. **Registry failures (network, TLS, 401/403, 5xx, redirect) raise `RegistryUnavailable` BEFORE anything is written, so the batch is retried; only message-level problems (no magic byte, unknown id, Protobuf schema, bytes not matching the schema) are dead-lettered**: never dead-letter on an outage. `avro_type` maps Avro to Arrow and feeds `build_batch(hints=)` for new columns (existing tables keep their types). DLQ rows carry `value_b64` (exact bytes; the DLQ write uses `schema_mode="merge"` so older DLQ tables gain the column). `fastavro` is a requirement (rebuild).   **Protobuf and JSON Schema** (`format: protobuf | jsonschema`, same `RegistryDecoder`, `kind` AVRO/PROTOBUF/JSON from the registry's `schemaType`; a schema of another type than the stream's is a message problem naming the format to choose). Protobuf: `_compile_proto` writes the registry's .proto plus its `references` (names validated: no absolute paths or `..`, max 50 files, size caps) into a temp dir and compiles with `grpc_tools.protoc` (`--descriptor_set_out --include_imports`, well-known types from grpc_tools' `_proto`) into a private `DescriptorPool` per schema id; the message index header (zigzag varints, single 0 byte = [0]) picks the message, nested ones via the index path; `proto_message` converts (enums as names, Timestamp as datetime, presence-aware for `optional`/messages). **`grpcio-tools` must stay `>=1.73,<1.77`: newer releases pull protobuf 7, which conflicts with dbt (`protobuf<7`)** (rebuild the image).   **Rewind / Move** (`web/stream_ops.py`; needs a STOPPED stream, else `StreamBusy` = HTTP 409). The position lives in the Delta table (application transactions), so lowering it needs a Delta commit: `_record` sets the txns and (mode `replace`) deletes rows `_topic = t AND ((_partition = p AND _offset >= o) OR ...)` in the SAME commit via `DeltaTable.delete(pred, commit_properties=...)` (an empty append carries the txns when nothing matched); the DLQ table gets the same (its columns are `partition`/`offset`, quote them). A plan is stored in `streams.pending` first and `finish_pending` (called by the ops functions, the runner start and `sync_runners` for stopped streams) applies it idempotently: DLQ table first, main table, then the definition + `stream_offsets` in one SQLite transaction (`stream_offsets` is normally MAX-only; ops REPLACE it). Move: same cluster (matching `cluster_id` from metadata; unknown = user must confirm) keeps positions; another topic or cluster REQUIRES a start position and overwrites the txns even for a same-named topic (app ids are `dkw-stream:<id>:<topic>:<partition>`, they would collide with the old cluster's offsets); a target move records the current offsets on the new table via a marker commit (fixes stale txns of an earlier life). `update_stream` still refuses to change connection/topic/target. - **Git review, forges and conflicts** (`web/git_review.py`, `web/git_sync.py`; endpoints `/api/git/repos/{kind}/diff|diff/file|discard|merge|merge/finish|merge/abort|conflicts|conflicts/file|conflicts/resolve`; UI: the `gitReview` modal opened by *Review changes*, shared by the dbt and notebooks panels). **Forges**: `Repo.forge()` (`GIT_FORGE`, else guessed from the host) drives `api_base`, `_api` (Gitea `token X`, GitHub `Bearer` + `X-GitHub-Api-Version`, GitLab `PRIVATE-TOKEN` + url-encoded project path incl. subgroups), `_pr_view`/`_pr_for_branch`/`_pr_create` (GitLab `iid`/`opened`/`merged`), and how git authenticates over HTTP (`_git_auth_header`: Gitea `token`, GitHub Basic `x-access-token`, GitLab Basic `oauth2`; `_scrub` also removes the base64 form). **A conflicting merge is now LEFT IN PROGRESS** (`update_from_base`, `merge_remote` for a diverged direct-mode branch) instead of being aborted: while `.git/MERGE_HEAD` exists `_refuse_during_merge` blocks pull/commit/push/PR/finish/abandon/discard/start_change, `status().merge` lists conflicts (`ls-files -u` stages: both_modified/both_added/deleted_by_incoming/deleted_by_you) and resolved files; `resolve` = ours/theirs/delete/keep/merged (hunk `choices` re-parsed server-side from the file's markers so line endings survive, or whole `content`; markers in typed text are refused)/reopen (`checkout -m`); `finish_merge` refuses unresolved files, leftover markers, `_problem_with_tree()` (dbt parse / notebook JSON) and `_problems_before_commit()` (secrets), then commits as the actor; `abort_merge` = `git merge --abort`. Every path from the client goes through `_safe_path` BEFORE any lookup (no `..`, no absolute, no `.git`, no symlink out) and must be in the changed / conflicted list. Naming: in a merge, "ours" = my branch (UI "Yours"), "theirs" = incoming. Alpine gotcha: a statement-style `@click.outside="if (...) x = y"` on the modal underneath makes Alpine throw `u is not a function` when clicking inside another modal; use an expression (`a || (b = c)`) and close the top modal with a deferred `closeGitReview()` so the underlying modal does not treat the close click as an outside click.
