1. Overview & Architecture

DataKilnWorks Studio is an enterprise-grade, local and on-premises Data Lakehouse and GenAI Platform. Designed as an uncompromised alternative to cloud-only data ecosystems such as Databricks and Snowflake, DataKilnWorks executes entirely on your hardware—delivering sub-second query latency, sub-20ms distributed worker autoscaling, and complete data sovereignty at $0 cloud operational cost.

Rather than relying on legacy Java Virtual Machine (JVM) clusters or proprietary cloud-locked query engines, DataKilnWorks synthesizes modern, high-performance open technologies into a unified operational canvas:

DuckDB Vectorized C++ Engine
Zero JVM cold starts, in-process SIMD vectorized query execution, sub-10ms analytics, and direct Apache Arrow streaming.
Ray Distributed Actor Pools
Sub-20 millisecond horizontal worker elasticity (0-16 workers), parallel Map-Reduce, and zero-copy Arrow memory via the Plasma Object Store.
Open Delta Lake ACID Storage
Full transaction log integrity (OCC), multi-version concurrency, time-travel queries, and automated compaction/vacuuming.
Unity Catalog Governance
3-level namespace (catalog.schema.table/model/volume), interactive lineage graph, and multi-user home isolation with RBAC.

Core Design Decisions

  • Zero JVM Overhead: By substituting the traditional JVM-heavy Apache Spark cluster with DuckDB and SQLFrame, memory consumption drops by 85%, eliminating garbage collection pauses, Java heap sizing, and slow cluster spin-up delays.
  • True Open Formats: All lakehouse tables are stored in Delta Lake (Parquet + JSON transaction log). There are no proprietary lock-in formats (such as Snowflake micro-partitions), ensuring full external interoperability.
  • Sub-20ms Elasticity: Scaling compute workers in standard cloud platforms takes 2 to 5 minutes. DataKilnWorks leverages Ray Worker Actors to allocate or release worker processes in under 20 milliseconds without restarting containers.
  • Complete Air-Gapped Operation: The platform operates 100% offline with zero external cloud dependencies, making it suitable for defense, healthcare, proprietary IP, and strict data sovereignty environments.

2. Workspace & User Environments

DataKilnWorks enforces enterprise-grade multi-tenancy and workspace isolation modeled directly on Databricks Workspaces. Every authenticated user is automatically allocated a private home environment with strict access boundaries.

Personal Home Directories (Users/<username>/)

Upon user creation or initial login, the workspace subsystem executes init_user_workspace(username) in web/workspace.py:

  • Creates the directory /workspace/notebooks/Users/{username}/.
  • Seeds an interactive personal starter scratchpad: {username}_scratchpad.ipynb.
  • Badges the folder in the UI with a distinct Home tag and house icon.
  • Auto-expands the user's home folder and loads their personal scratchpad notebook upon login.
RBAC Boundary & HTTP 403 Enforcement

Non-admin users (role == 'user' or 'power_user') are strictly isolated. Any attempt to read, write, rename, or delete files in another user's personal directory (e.g. analyst_bob accessing Users/admin/...) is intercepted by can_access_workspace_path() and returns an immediate HTTP 403 Forbidden response.

Notebooks are per user and run inside the studio

There is no separate JupyterLab server. Notebooks are edited and run in the embedded runner, every notebook endpoint requires a valid session, and each user reaches only Users/<their name> and Shared (administrators reach everything). Kernels are per user and notebook, so two users on the same shared notebook never share variables. Users a masking policy applies to run in the notebook sandbox: a separate container with no access to the warehouse files, a separate OS user per person, and no network besides the studio. Their spark, conn and %sql read data through the governance gateway, so it arrives masked. Warehouse files, dbutils and writes to the warehouse are not available there. If the sandbox is not running, they can read and edit notebooks but not run them.

Scratchpad Notebooks & PySpark via SQLFrame

Personal scratchpads support Python, SQL, and PySpark DataFrame code. Through the built-in SQLFrame engine, you can write idiomatic PySpark code that executes directly on DuckDB without starting a JVM:

Users/analyst_bob/analyst_bob_scratchpad.ipynb
Python (PySpark / SQLFrame) 
# Native PySpark DataFrame execution on DuckDB without JVM
from sqlframe.duckdb import SparkSession
from pyspark.sql.functions import col, sum as _sum, avg, to_date

spark = SparkSession.builder.getOrCreate()

# Read directly from an ACID Delta Lake table in Unity Catalog
df = spark.read.table("warehouse.dbo.silver_yellow_tripdata")

# Standard PySpark transformations
summary_df = (
    df.filter(col("trip_distance") > 0)
      .groupBy("payment_type")
      .agg(
          _sum("total_amount").alias("gross_revenue"),
          avg("trip_distance").alias("mean_distance")
      )
      .orderBy(col("gross_revenue").desc())
)

# Output rendering
summary_df.show()

3. Catalog & Governance (Unity Catalog)

DataKilnWorks implements full Unity Catalog 3-level namespace compatibility: catalog.schema.table.

Namespace Architecture & Cross-Catalog Joins

Catalogs are stored in separate directories under ./warehouse/catalogs/{catalog_id}/. When querying multiple catalogs, secondary catalogs are mounted into DuckDB via in-memory ATTACH. This enables zero-copy joins across isolated catalogs in a single SQL statement:

Cross-Catalog SQL Join
SQL 
-- Seamless cross-catalog query across warehouse and finance catalogs
SELECT 
    w.employee_id,
    w.employee_name,
    w.department,
    f.salary,
    f.annual_bonus,
    (f.salary + f.annual_bonus) AS total_compensation
FROM warehouse.dbo.silver_employees w
JOIN finance_lake.payroll.salary_records f 
    ON w.employee_id = f.employee_id
WHERE w.active = true
ORDER BY total_compensation DESC;

Delta Lake ACID Logs & Time Travel

Every table mutation writes a forward-compatible JSON commit to the table's _delta_log/. DataKilnWorks supports historical point-in-time reads and rollbacks via standard time-travel syntax:

Delta Lake Time Travel Queries
SQL 
-- Query historical version by commit version number
SELECT * FROM delta_table_version('warehouse.dbo.silver_employees', 2);

-- Compare changes between current snapshot and version 1
SELECT 
    curr.employee_id,
    curr.salary AS current_salary,
    prev.salary AS historical_salary,
    (curr.salary - prev.salary) AS salary_change
FROM warehouse.dbo.silver_employees curr
JOIN delta_table_version('warehouse.dbo.silver_employees', 1) prev
    ON curr.employee_id = prev.employee_id
WHERE curr.salary <> prev.salary;

Delta Shallow Clone

A shallow clone creates a new, independent Delta table from an existing one without copying any data: the clone gets its own transaction log and shares the source's immutable Parquet files. It is instant, costs no extra storage until the clone changes, and is ideal for testing a pipeline change or freezing a table at a point in time. Use Clone on a table in the Catalog explorer, the SQL editor, or the REST API.

Shallow Clone
SQL 
-- Clone the latest version (names must include the schema; a catalog is optional)
CREATE TABLE dbo.silver_employees_test SHALLOW CLONE dbo.silver_employees;

-- Clone an earlier version, by number or by time
CREATE OR REPLACE TABLE dbo.silver_employees_v2 SHALLOW CLONE dbo.silver_employees VERSION AS OF 2;
CREATE TABLE IF NOT EXISTS dbo.silver_employees_1h SHALLOW CLONE dbo.silver_employees TIMESTAMP AS OF '2026-09-24 10:00:00';

-- Across catalogs
CREATE TABLE sandbox.scratch.emp SHALLOW CLONE warehouse.dbo.silver_employees;
  • Hard links, not references: unlike Databricks, where a clone points at the source's files and breaks if the source is vacuumed, the clone here hard-links those files into its own directory. It stays valid if the source is vacuumed, rewritten or dropped, and both readers (delta-rs and DuckDB) see an ordinary table. Source and target must be local catalogs on the same filesystem; a table using deletion vectors or row tracking cannot be cloned.
  • Independent afterwards: writes, deletes, merges and vacuum on either side never affect the other. The clone's first commit (version 0) is an audited CLONE entry that records the source and version.
  • Governance: because a clone shares raw files, a user that a masking or row-filter policy applies to cannot clone at all. For everyone else the clone receives the source's tags (including tags the source inherited from its schema or catalog) before it exists, so masking and row filters keep applying to it. Cloning needs read access to the source catalog and write access to the target catalog.
  • REST: POST /api/table/{schema}/{table}/clone with {"target_table": "...", "target_schema": "...", "target_catalog": "...", "catalog": "...", "version": N, "timestamp": "...", "replace": false, "if_not_exists": false}.

Unity Catalog Volumes

Volumes govern unstructured and semi-structured assets (raw CSVs, PDF documentation, model weights, audio, images). Volumes are addressed via POSIX-compliant paths:

/Volumes/<catalog>/<schema>/<volume_name>/path/to/file.ext

  • Managed Volumes: Storage is hosted and governed directly inside the studio storage layer (./warehouse/volumes/{catalog}/{schema}/{volume}/).
  • External Volumes: Mapped to external storage mounts, NFS, or S3-compatible endpoints.
  • Auto-Loader: a volume can be watched by an Auto-Loader pipeline that ingests new files into a Delta table.
  • Interactive Volume Explorer: Browse directories, upload files via drag-and-drop, and generate presigned download links directly within the UI.

Interactive Data Lineage (22-Node DAG)

The Data Lineage workbench visualizes column-level and table-level lineage. The engine statically parses SQL DDL/DML, dbt schemas, and Delta log operations to construct an interactive Directed Acyclic Graph (DAG) displaying upstream sources and downstream consumers.

Tags, Tag-Driven Masking Policies & Row-Level Security

Tags classify data once; masking policies then protect every column carrying a tag, and row filter policies restrict which rows of every table carrying a tag are visible, wherever they are queried. Tags can be attached to catalogs, schemas, tables and columns, are stored in SQLite (warehouse/.metadata/governance.db), and are inherited downwards: a tag on a schema applies to every table and column beneath it, and a more specific tag overrides the inherited one.

  • Tags: a key with an optional list of allowed values (for example pii = email, phone, name). Manage them in the Governance view (admins) or from the Tags column of the catalog explorer schema tab.
  • Masking policies: bind a tag (and optionally a value) to a mask, with exemptions by role, user or group (members of an exempt group see the raw values; leaving the group ends it on the next query). Built-in masks: full, partial, email, null, hash (keyed, so it cannot be reversed by a dictionary attack), date_year, round and a validated custom SQL expression. Each mask states what it does per column type.
  • Row filter policies (row-level security): bind a tag on a catalog/schema/table (never a column, since a row filter restricts the whole table) to a column and a mode: owner (that column must equal the caller's username), attribute (that column must be one of the caller's assigned values for a key, from a built-in membership table you populate under Row Filters → User attributes — nothing assigned means nothing visible, never everything) or a validated custom boolean expression using {col}/{user}/{role}. Several applicable policies on one table combine with AND.
  • Enforcement at query time: a gateway rewrites the SQL of every governed execution path (SQL editor, dashboards, Genie, alerts, scheduled exports, jobs, time travel, Auto-Loader, compute nodes) into SELECT * [REPLACE (...)] FROM table [WHERE predicate AND ...], using scope analysis so that CTEs, joins, subqueries, aliases and SELECT * cannot bypass it. It fails closed: SQL it cannot analyse is refused, and users a policy applies to may only run allow-listed read statements.
  • Suggestions: the classifier proposes tags for untagged columns (emails, phone numbers, names) which an admin accepts in bulk.
  • Preview as user: shows which columns another user sees masked, which tables have a row filter applied for them, and the rewritten SQL, without impersonating them.
  • Groups in policies: both masking and row-filter policies can exempt whole groups (Exempt groups in the policy form). For attribute-mode row filters, Assign to: a group gives a group its own attribute values (e.g. the EMEA team gets region = EMEA): a member sees the union of their own, their role's and all their groups' values, so belonging to more groups can only show more rows, and no value at all still means no rows. Membership is read on every query, so joins, leaves and directory syncs take effect immediately. Deleting a group removes it from every policy's exemptions (the policy becomes stricter, never looser) and deletes its attribute values. A notebook kernel that is already running keeps the execution route (sandbox or not) it started with until it is restarted.
  • Tag propagation: when an exempt user runs CREATE TABLE ... AS SELECT over tagged columns, the tags follow onto the new table (computed columns are marked sensitivity=unclassified for review). A copy of a row-filtered table is tagged the same way as its source, so a copy cannot become a full unfiltered leak of the original.
  • Audit & coverage: every tag and policy change is logged, and the coverage view shows which execution paths are governed, how many sensitive columns are still untagged, and which row filter policies match nothing or reference a missing column.
SQL 
-- An analyst with a policy on pii=email sees masked values; an admin (exempt) sees raw values
SELECT name, email FROM warehouse.hr.employees;
-- name | email
-- Ada  | a***@example.com

-- With a row filter policy (attribute mode, column "region") the analyst also sees only their assigned regions:
SELECT name, region FROM warehouse.hr.employees;
-- name | region
-- Ada  | EMEA
Limits of masking and row filtering

Both are enforced in the studio's SQL layer. Notebook kernels run arbitrary Python and cannot be masked or row-filtered, so users either policy applies to run them in the isolated notebook sandbox, where data is only reachable through the governance gateway (see Security Settings). Direct file access to the warehouse is only possible for administrators.

Query History: reuse and fix old queries

Query History is an audit trail: what ran is never rewritten. Opening an entry (Inspect) shows its SQL in an editable working copy. Qualify table names completes every table name to catalog.schema.table by inserting the missing prefix in place (your formatting and comments stay). A name is only completed when it resolves to exactly one table; unknown or ambiguous names are listed and left alone, as are CTE names and table functions. From there use Open in SQL editor or Save as query to keep the corrected version under Saved Queries.

The history is append-only for everyone except administrators: only an admin sees the checkboxes and Delete selected (and Clear History). Every deletion is written to the governance audit log (HISTORY_DELETE / HISTORY_CLEAR: who, how many, which query ids; never the SQL text). Saved queries are not affected.

SQL Warehouses (Dynamic Compute Sizing)

Compute endpoints allow isolating analytical workloads from transformation jobs. Warehouses can be scaled dynamically across T-shirt sizes:

  • 2X-Small: 1 vCPU, 1 GB RAM (Ad-hoc testing, scratchpad exploration)
  • Small: 2 vCPU, 4 GB RAM (General querying)
  • Medium: 4 vCPU, 8 GB RAM (Standard BI & dashboards)
  • Large: 8 vCPU, 16 GB RAM (Complex aggregations & joins)
  • 2X-Large: 16 vCPU, 32 GB RAM (Heavy ETL & compaction jobs)

Auto-suspend and auto-resume are real. A warehouse that has been idle for its Auto-Stop timeout has its compute-node container stopped, releasing its memory (or paused, with WAREHOUSE_SUSPEND_MODE=pause: frozen, instant resume, memory kept). The next query resumes it automatically: the studio starts the container, waits until the worker answers (a few seconds) and runs the query there, and the result reports how long the resume took (warehouse_resumed_ms). Concurrent queries share one resume, a running query is never interrupted, and the idle clock starts when work ends. Start and Stop on the SQL Warehouses page act on the container too (administrators and power users only), and a container stopped by hand is noticed.

  • Warm start: each warehouse chooses in its dialog what an idle compute node does. Stops frees the memory, and the next query is a cold start of a few seconds (the table shows last resume ... (cold start)). Stays warm freezes the node instead (Docker pause): the next query resumes in milliseconds, at the price of the memory staying allocated; Hold warm for limits that price (30 minutes to 24 hours, then the node is really stopped, so the next query is a cold start again). The choice overrides the deployment default WAREHOUSE_SUSPEND_MODE. Warm-up tables (at most 10, catalog.schema.table) are read once by the worker right after a cold start, so the first query does not pay for loading the engine's Delta support and cold metadata; the warm-up runs in the worker, returns nothing to anyone and a failure only becomes a warning on the resume. The SQL editor reports the kind of resume (warehouse_resume_kind: warm or cold).
  • Docker socket isolation: the studio never holds the Docker socket (that would be root on the host). The container-controller service does, and only offers start / stop / pause / unpause of an allow-list of this project's compute-node services, authenticated with a token on an internal network shared only with the studio. Everything else it refuses with a 404.
  • Rootless Docker: the socket lives at $XDG_RUNTIME_DIR/docker.sock; set DOCKER_SOCKET_PATH in .env (e.g. /run/user/1000/docker.sock).
  • When it is not enforced: without the controller, or for a warehouse whose endpoint is not one of the managed compute nodes, the timeout is only a setting; the page shows not enforced and Start / Stop only change a flag. Tuning: AUTOSUSPEND_INTERVAL_SECONDS (check period, default 30) and WAREHOUSE_RESUME_TIMEOUT (default 60).

5. Data Engineering & Pipelines

Data Ingestion ("Add Data" Wizard)

The Data Ingestion Wizard allows drag-and-drop ingestion of raw files into Delta Lake tables:

  1. Upload: Drop .csv, .tsv, .parquet, or .json files into the upload target.
  2. In-Process Schema Inference: DuckDB samples the file in-process to infer column headers, data types, and nullability without loading the entire file into memory.
  3. Destination Configuration: Pick the target catalog from a dropdown, then type the schema (e.g. bronze) and destination table name. The dropdown lists the local catalogs and every writable S3 mount (marked S3); read-only mounts and mounts that are not Delta stores (e.g. PostgreSQL) are not offered and are refused by the API. For an S3 catalog the table is written to s3://<bucket>/<schema>/<table> with that mount's endpoint and credentials, and append, merge and schema evolution work as they do locally.
  4. File format: a dropdown (CSV, TSV, Parquet, JSON, JSON Lines, NDJSON) sets the file pattern; Custom pattern… accepts any glob such as sensor_*.csv.
  5. Connections (HTTP(S) files, REST APIs, SFTP): the Connections button saves the login for an external server once (administrators create and edit; power users can pick them). The secret (token, password, private key) is stored encrypted, is never shown again and never appears in logs, the audit trail or an API response. A pipeline chooses Connection as its source, picks the connection and adds a path; it can only extend the connection's base URL or folder, so the login can never be sent to another host. Connection sources are polled (an interval or a cron schedule); file events do not apply.
    • HTTP(S) file: the file is loaded when it is new or changed (ETag / Last-Modified, otherwise by its content); an unchanged file is not downloaded again. The format comes from the URL's extension or the server's content type.
    • OAuth 2.0 client credentials for REST APIs. An HTTP(S) file / REST API connection can authenticate with OAuth 2.0 client credentials, the machine-to-machine grant used by Entra ID app registrations, Okta / Auth0 / Keycloak service clients and most vendor APIs. Enter the token URL, the client ID, the client secret (stored encrypted like every connection secret and never shown again), an optional scope, how the credentials are sent (an HTTP Basic header, the default per RFC 6749, or in the request body, which some providers such as Auth0 require) and optional extra token parameters such as audience=https://api.example.com. The studio then fetches the access token itself, keeps it in memory only, refreshes it shortly before it expires and once more if the API answers 401 (a revoked token), so a pipeline that polls for weeks keeps working. Test fetches a token and reports its lifetime, then calls the base URL; a refused client shows the provider's own reason (for example invalid_client) and never the secret. Safety: the secret goes to the token URL only and the token to the connection's base URL only (the base-URL origin rule is unchanged); the token URL must be https unless you tick allow insecure for a trusted internal server; redirects from the token endpoint are not followed; the answer is size-limited and a token containing spaces or line breaks (header injection) is refused; only Bearer tokens are supported. Not covered: the authorization-code / refresh-token flows (a person signing in), JWT-bearer client assertions and mutual TLS.
    • REST API returning JSON: set the records path (e.g. data.items), optional query parameters and pagination (page number, offset + limit, or a next link in the response). Every poll fetches all pages as one snapshot; an unchanged response is skipped. For an API that returns the current state use Merge (with key columns) or Overwrite; Append would add the records again whenever anything changes.
    • Preview for volume folders and S3. A local volume folder (/Volumes/... or a path in the warehouse) and an s3://bucket/prefix/ source have the same Preview first rows button in the create dialog. It applies the pipeline's own rules: the file format / pattern you chose, the same filters (hidden files and folders, .tmp / .part, _quarantine; sub-folders included) and the same reader, and it shows the columns with their types and the first rows of the oldest matching file, which is what the pipeline loads first. The matching files are listed as buttons: click one to preview that file instead. Files whose format the loader does not read are marked and counted. S3 objects are read in place through the storage mount (automatic, or the one you picked): a Parquet object costs a few range requests, nothing is downloaded, and a prefix with a huge number of objects is only scanned up to 3000 keys (the preview says so). Nothing is created, checkpointed or loaded, a folder that does not exist yet is reported instead of being created, and a corrupt file, a missing bucket or wrong credentials are explained in one line (the secret is never in a message). Hidden folders of the warehouse (.metadata holds credentials) can never be a source, for a preview or for a pipeline.
    • SFTP: password or private-key login. The server's host key fingerprint is pinned in the connection (press Test to see it, compare it with the one your provider publishes, press Pin this) and is checked on every connect: a changed or impersonated server is refused. Files matching the pattern are loaded once each (path + size + modification time); a file still changing (within the settle time, default 10 s) waits for the next poll. Sub-folders are optional.
    Preview: before creating a pipeline, Preview first rows in the create dialog reads the source right then and shows its columns (with types) and the first rows: an HTTP file (up to 20 MB), a REST API's first page only (the pipeline itself fetches every page), or the oldest matching file of an SFTP folder together with the names of the others. It makes the same request the pipeline would, so a wrong records path, a refused login or an unreadable file is explained there instead of after the first poll; nothing is loaded, checkpointed or kept. Nothing on the remote side is ever changed or deleted. Downloads are capped at 1024 MB (AUTOLOADER_MAX_DOWNLOAD_MB). A corrupt download is quarantined locally and not retried; an unreachable server or refused login sets the pipeline to ERROR and is retried on the next poll.
  6. Write Strategy: Choose between Overwrite (replace table) or Append (add rows).
  7. ACID Materialization: The engine writes Parquet columnar files and commits the transaction into the table's _delta_log/.

Auto-Loader Pipelines (Volume to Delta)

Auto-Loader pipelines incrementally ingest files that land in a Volume into a Delta table, tracking which files were already loaded so each file is processed once.

  • Formats: CSV, JSON, Parquet and text, with schema inference and schema evolution.
  • Write modes: append or merge on one or more keys (key values are escaped, so odd column names are safe).
  • Rescued data: values that do not fit the schema land in a rescued-data column instead of failing the run.
  • Streaming-style batches: large loads are processed in batches (AUTOLOADER_BATCH_ROWS) with per-run history.
  • Triggers: a poll interval (5 s and up), a cron schedule, on demand, or File events: the pipeline starts as soon as a file is completely written or renamed into the folder (Linux inotify; typically about a second). A file that is still being written is never loaded; hidden, .tmp, .part and non-matching files are ignored, and a burst of files becomes a few runs. A low-frequency safety-net rescan (default every 5 minutes) still runs, because filesystem events can be missed on network drives or while the studio is down, and a catch-up run starts whenever watching starts. If inotify is unavailable the card shows watch unavailable and the pipeline keeps polling. File events and a cron schedule are alternatives.
  • S3 and S3-compatible buckets: set the source to s3://bucket/prefix/ (AWS S3, MinIO, Garage, Ceph, R2, ...) and pick an S3 storage mount (added with Mount in the catalog) for the endpoint and credentials. Each poll lists the prefix and streams new objects straight from the bucket into Delta without downloading them. An object counts as new when its key, size or ETag is new; identical bytes uploaded again are not reloaded. Objects under hidden folders, _quarantine/, .tmp/.part files and non-matching names are ignored. A malformed object is copied under _quarantine/ and deleted from its original key when the credentials allow it. S3 sources use a poll interval (30 seconds or more recommended, since every poll is a list request) or a cron schedule; File events is local-only.
  • S3 bucket events (instant, no polling): instead of listing the bucket every few seconds, let the bucket tell Data Kiln Works. An administrator opens S3 events at the top of the Auto-Loader view, creates an access token (shown once, stored only as a hash, revocable) and copies the receiver URL (/hooks/s3-events). MinIO is pointed at it with mc admin config set ALIAS notify_webhook:dkw endpoint=<URL> auth_token=<token>, a service restart and mc event add ALIAS/BUCKET arn:minio:sqs::dkw:webhook --event put; Garage and any S3-compatible server that can POST S3 event JSON with an Authorization: Bearer header work the same way. Then choose S3 events as the polling interval of an s3:// pipeline. An event only wakes the pipeline: what it loads still comes from listing the bucket, so a forged, repeated or lost event can never load anything wrong. Only object-created events for a key under the pipeline's prefix that matches its file pattern (and is not hidden, .tmp/.part or under _quarantine/) count; a burst of uploads starts one run (debounce of S3_EVENTS_DEBOUNCE seconds, default 2), events during a run cause exactly one more run, and a low-frequency safety-net rescan (default 5 minutes) catches events lost to a restart or a network problem. S3 events are an alternative to a cron schedule and to file events. The dialog for the events shows each pipeline's wake count, last event and last run and the recent notifications. If you use an IP allowlist, allow the bucket server's address, since the receiver is called by it and not by a browser.
  • Lineage: the source Volume appears as a node in the lineage graph.
  • Governance: ingestion runs as the pipeline owner, and tags propagate to the target table.

Streaming Ingestion (Kafka / Redpanda to Delta)

A stream continuously loads one Kafka topic into a Delta table in micro-batches (Apache Kafka, Redpanda, Confluent Cloud, MSK and other Kafka-compatible brokers). Open it with the Streams button of the Auto-Loader view (administrators and power users).

  1. Create a Kafka connection (Connections > Type Kafka / Redpanda): bootstrap servers (host:port, comma-separated), the security protocol (PLAINTEXT, SSL, SASL_SSL, SASL_PLAINTEXT), the SASL mechanism (PLAIN, SCRAM-SHA-256, SCRAM-SHA-512), user name and password, a CA certificate for a private CA and, for Avro, Protobuf or JSON Schema topics, the Schema Registry URL with an optional user/API key and password. Passwords are stored encrypted and never shown again. A password over SASL_PLAINTEXT is refused unless you tick allow for a trusted internal broker. Test connects to the brokers (and the registry) and reports a rejected login or a TLS problem in plain words.
  2. Create a stream: pick the connection, the topic (the list shows what the login can see), the target catalog/schema/table, the format, where to start (earliest = the whole topic, latest = only new messages), the batch size and the maximum wait per batch. Preview newest messages shows the columns and types the table would get, and how many messages would be dead-lettered, without creating anything.
  3. Watch it: the list shows the status (running, error, stopped), rows loaded, lag (messages behind the end of the topic), the last batch and the last error. Stop and Start pause and resume; a stopped stream resumes exactly where it ended. Rewind and Move (stopped streams only) are described below.
  • Exactly-once. Each Delta commit records, per partition, the next offset to read (Delta application transactions), so the table itself says how far it has been loaded. After a crash, a restart or even a wiped studio database the stream resumes from the table, and no message is loaded twice; a batch interrupted before its commit is loaded once. Consumer-group offsets are also committed to Kafka after each batch so external lag tools work, but they are never used to resume.
  • Columns. The first batch defines them: numbers become bigint/double, true/false boolean, everything else text; nested objects and arrays are stored as JSON text (query them with DuckDB's JSON functions). Every row also gets _key, _topic, _partition, _offset, _timestamp and _rescued_data. Timestamps in the payload stay text unless the target column is a timestamp.
  • Schema drift never stops the stream. A field the table does not have, or a value that does not fit its column, is kept as JSON in _rescued_data. With Add new fields as columns new fields become columns instead. The format Text loads the message as one column value.
  • Schema Registry formats (Avro, Protobuf, JSON Schema). Choose Avro, Protobuf or JSON Schema (Schema Registry) as the format for Confluent-style topics (magic byte 0 + schema id + payload). The schema of each message is fetched from the registry by its id and cached, so the table's columns and types come from the schema, not from guessing. A message written with a newer schema version loads too: its new fields go to _rescued_data, or become columns with Add new fields; a value that does not fit its column is rescued as well. A registry-encoded message key is shown as JSON text in _key. If the registry cannot be reached (network, TLS, refused login, HTTP 5xx) the stream shows the error and retries; nothing is dead-lettered and nothing is skipped meanwhile. Redirects from the registry are not followed, so the login never leaves. A message whose schema is of another type says which format to choose. In every format, records, arrays, maps and nested messages are stored as JSON text.
    • Avro: int = int, long = bigint, float/double, boolean, string and enum as text, bytes/fixed as binary, decimal as decimal, date, timestamp-millis/micros as timestamp (UTC); a union with null is its other branch.
    • Protobuf: the .proto (and the files it imports, through the registry's references) is compiled with protoc, and the message index in the message header selects the message type (also nested ones). int32/int64 as is, uint32 as bigint, uint64 as decimal(20,0), float/double, bool, string, bytes as binary, enums as their names, google.protobuf.Timestamp as timestamp (UTC); repeated fields, maps and messages as JSON text. An optional field or an unset message is null; a plain proto3 field that is not set has its default value (0, empty), as protobuf itself cannot tell the difference.
    • JSON Schema: integer = bigint, number = double, boolean, string (format: date-time as timestamp, date as date); objects and arrays as JSON text; ["null", X] and anyOf with null are X. Messages are not validated against the schema, but a value of the wrong type is rescued.
  • Dead letters. A message that cannot be decoded (not valid JSON or not an object; for the registry formats: no wire-format header, an unknown schema id, a schema of another type, bytes that do not match the schema) goes to <table>_dlq (topic, partition, offset, timestamp, key, value, error, ingested_at and value_b64, the exact bytes of a registry-format message, so binary messages can be re-decoded or replayed later) and the stream continues. A message without a value (tombstone) is skipped.
  • Partitions and restarts. A partition added later is read from its beginning. A stream that cannot reach the broker or is refused shows the reason and retries with a growing delay. If the broker's retention deleted messages the stream had not read yet, it continues from the oldest available and says so in the last error.
  • Lineage and downstream. The topic appears in the lineage graph feeding the table. The table is an ordinary Delta table, so a workflow can start when it changes (Delta table changed trigger).
  • Rewind. Rewind reads the topic again from earliest, latest (skip what is waiting), a date and time (UTC) or explicit offsets per partition. Because the position is recorded in the Delta table itself, a rewind is a Delta commit that lowers those recorded offsets. Choose what happens to rows already loaded: Replace (default) deletes the rows at or after the new position, and the matching dead letters, in the same commit, so the re-read messages replace them and nothing is duplicated; Keep leaves them and the messages are appended again (duplicates, on purpose). Show what will happen is a dry run: per partition where the stream is, where it will be, what the broker still holds and how many rows would be deleted. A position older than the broker's retention is moved to the oldest message that still exists, and says so. The stream must be stopped.
  • Move. Move changes the connection, the topic and/or the target table of a stopped stream. Another connection to the same Kafka cluster (the cluster ids must match; if the broker reports none you are asked to confirm) and another table keep the position: the stream continues without re-reading or skipping, and an existing target table with old recorded offsets is corrected. Another topic or another cluster starts at the position you choose (earliest, latest, a date and time, or an offset for every partition), because offsets mean nothing on another topic; this also holds for a topic with the same name on another cluster. The data already loaded stays in the table. A table that another stream loads, a topic that does not exist and a connection that is not a Kafka connection are refused, and a dry run shows the change first.
  • Interrupted operations. A rewind or move is written down before it is applied and every step can be repeated, so a crash halfway is finished automatically the next time the stream (or the studio) starts.
  • Limits. Rewinding a running stream is not possible (stop it first). Protobuf needs the message's schema to compile with protoc (very unusual proto features such as extensions are not decoded into columns).

Initialisation & Kubernetes

python -m web.init is a one-shot step that runs before the studio starts. It exists so that a misconfigured deployment fails once, with a readable message, instead of putting the studio into a restart loop. In Docker Compose it is the datakilnworks-init service (the studio waits for it to succeed); in Kubernetes it is an init container of the studio pod (same image, different command). docker compose logs datakilnworks-init / kubectl logs <pod> -c init shows what it did.

  • Bootstrap admin. When there is no account yet, a missing or malformed INIT_ADMIN_PASSWORD_HASH (or an unusable INIT_ADMIN_USERNAME) fails the init with the reason. On an already-initialised warehouse these variables are not needed and are ignored.
  • Databases. Every SQLite database (accounts, governance, history, lineage, groups, streams, SCIM, MFA policy, IP allowlist, connections, job runs, ...) is created or migrated once, before the studio and its background loops open them.
  • Seeding and volumes. The dbt project directory is seeded from the template (only missing files; a project that already has a dbt_project.yml is left alone), the warehouse / notebook / project directories are created, and each is checked for write access. A volume owned by another user fails with a hint (securityContext.fsGroup in Kubernetes, chown in Docker).
  • Warnings. Optional packages missing from the image (for example an image built before a requirements change: dbt-duckdb, confluent-kafka, fastavro, grpcio-tools) are reported as warnings naming the feature that will not work, so a stale image shows up at deploy time.
  • Waiting. --wait-for URL[,URL] (or INIT_WAIT_FOR) waits until other services answer (any HTTP status below 500), and fails after --wait-timeout.
  • Safe to repeat. Every step is idempotent, and a lock on the warehouse serialises concurrent runs (two pods, a re-run). The studio answers /healthz (liveness: the process is up) and /readyz (readiness: the accounts database can be read and the warehouse exists) without a login and without any data; they are exempt from the IP allowlist so that a kubelet or load balancer can use them. The container controller (Docker socket) and the notebook sandbox are not part of the chart; see deploy/helm/README.md. The chart was rendered and linted but not installed on a live cluster.

Jobs & Pipelines (Local Workflows DAG)

The Jobs & Pipelines engine orchestrates multi-task workflows without requiring external schedulers (such as Apache Airflow or Celery). Supported task types include:

  • SQL Transformation (sql): Vectorized SQL executed directly in DuckDB.
  • Delta Maintenance (optimize): Compaction and bin-packing via OPTIMIZE and vacuuming via VACUUM.
  • Headless Notebook (notebook): Parameterized execution of .ipynb notebooks via Papermill.
  • File Ingestion (ingest): Automated pickup of landing zone files into Delta tables.

Reliability: retries, timeouts, run conditions

  • Retries: each task can retry up to 10 times with a delay and an exponential backoff factor; every attempt (status, duration, error) is kept in the run.
  • Timeouts: per task and for the whole job. A timed-out SQL statement is interrupted; other task types (notebooks, ingestion) are abandoned and their result ignored. A job that runs out of time ends TIMEOUT.
  • Run if: all succeeded (default), none failed, all finished, one succeeded, one failed, all failed. Use one failed / all finished for error handlers and cleanup tasks. A task whose condition is not met is SKIPPED.
  • Concurrency: Max concurrent runs (default 1). A run started while the limit is reached is recorded as SKIPPED instead of piling up.
  • Cancel and repair: a running run can be cancelled (a running SQL statement is interrupted, a wait between retries ends at once). Repair run re-runs only the tasks that did not succeed in a failed, cancelled or timed-out run, with the same parameters; succeeded tasks are reused.
  • Missed schedules: a run left RUNNING by a restart is marked FAILED; with catch up a schedule tick missed during downtime runs once after the restart.
  • Tasks of one run execute one after another in dependency order (there is no parallel execution of tasks within a run).

Parameters

Declare parameters on the job (name, default, optional allowed values or a regular expression) and reference them as {{ params.name }} in SQL and notebook parameters. Run Now asks for the values. Because a job runs with its owner's rights, every value is checked before it is substituted: by default only letters, digits and _ . : @ - space (max. 100 characters) are accepted, so a value can never break out of a SQL string; an allowed list or your own pattern replaces that rule. A reference to an undeclared parameter is refused when the job is saved.

Triggers

  • After another job succeeds, fails or finishes (chains are limited to 5 deep and a loop is stopped).
  • Auto-Loader ingested files: "file arrived" - runs when a pipeline ingested at least N files in a cycle.
  • Delta table changed: runs when the table gets a new version (checked every 15 s; the job's own writes do not retrigger it).

Notifications

Per job, choose the events (failure, success, cancelled) and a channel: email (comma-separated addresses, SMTP settings of the studio), Slack or a configured webhook. The message names the failing tasks and their errors; the delivery result of each channel is stored with the run and shown in the run details. A failing channel never affects the run.

Identity, Authentication & Governance

DataKilnWorks includes a native security stack supporting enterprise authentication protocols:

  • Role-Based Access Control (RBAC): Three built-in roles: admin (full platform governance), power_user (pipeline/model authoring), and user (query execution & reporting).
  • SAML 2.0 single sign-on: in Settings > Authentication > SAML enter (or Import from metadata URL) the identity provider's entity id, single sign-on URL and signing certificate, set the Studio public URL, tick Enable, save, and give the IdP's administrator this studio's metadata (/api/auth/saml/metadata; the assertion consumer service is <public URL>/api/auth/saml/acs). The login page then shows Sign in with <label>. Sign-in is strict: the assertion must be signed by the configured certificate, name this studio as audience, answer a sign-in this studio started and be within its validity window; each assertion works once, and on https the response must come from the browser that started the sign-in. IdP-initiated sign-in is off unless you allow it. Accounts are created as SAML accounts (no password); an existing local, LDAP or OIDC username, or a deleted or deactivated account, is refused. The role comes from the group attribute (Admin value / Power user value, else the default role), and a platform group can be mapped to a value of that attribute (see Directory group sync). Not supported: signed requests, encrypted assertions and single logout.
  • Groups: in IAM > Groups an administrator creates named groups and adds users to them: local, LDAP and OIDC accounts alike. Grant a group access instead of granting it person by person: a person's access is the highest of what they hold themselves and what any of their groups hold. Groups only ever add access and never change a user's role (admin, power user, user). Where a group can be granted access:
    • Catalogs (and so every table in them): choose Group in the catalog's access dialog and pick READ, WRITE or ADMIN. SQL is checked against these grants too.
    • Dashboards: A group in the dashboard's permissions, as viewer or editor.
    • Saved queries: the owner's Share button gives users or groups View (see and run) or Edit (also change). Only the owner or an administrator deletes a query or changes who it is shared with. Sharing never widens data access: the query still runs with each person's own permissions.
    • Auto-Loader pipelines: Share on a pipeline gives users or groups Run (trigger it) or Manage (also change, reset and delete it). Administrators and power users manage every pipeline as before; a plain user needs a grant to run one.
    Directory sync: a group can be mapped to an LDAP group (its DN; Browse… lists the directory's groups) or to a value of the OIDC groups claim. Members of that directory group are then added to the platform group when they sign in, on Sync LDAP now and on every LDAP sync (which also provisions new directory users), and are removed when the directory says they left; they are marked via directory and cannot be removed by hand. Members you added manually are never touched by sync, and if the directory cannot be asked (search base wrong, server down, or an OIDC token without a groups claim) nobody loses access. Changing or clearing a mapping removes the members that came from it. OIDC membership is refreshed at sign-in only. Deleting a group removes every grant it held. Group and grant changes are written to the audit log (GROUP_*, GRANT_*).
  • Tables and schemas: in a table's Access tab (catalog owners and administrators) Share this table or Share schema gives a user or group Select (read) or Modify (also write) on just that table, or on every table in the schema, including ones created later, without access to the rest of the catalog. It only ever adds access: catalog-level access above is unaffected, and masking and row filters still apply. Someone with only table grants sees the catalog in the explorer with just those tables, read-only, and can query them with a plain SELECT that names them as catalog.schema.table; a statement that cannot be verified that way (a two-part name, several statements, DML, a function under the catalog, anything the parser does not fully understand) is refused. SQL: the same grants can be managed from the SQL editor: GRANT SELECT ON TABLE sales.dbo.orders TO GROUP analysts, GRANT SELECT, MODIFY ON SCHEMA sales.dbo TO USER alice, GRANT SELECT ON FUTURE TABLES IN SCHEMA sales.dbo TO GROUP analysts, GRANT ALL PRIVILEGES ON CATALOG sales TO GROUP owners, REVOKE SELECT ON TABLE ... FROM ... and SHOW GRANTS [ON <object>] [TO USER|GROUP <name>] (with no arguments it lists your own). Privileges are read (SELECT, USAGE, USE CATALOG) or write (MODIFY, INSERT, UPDATE, DELETE, CREATE), and ALL PRIVILEGES; write includes read, so GRANT only ever raises what someone holds, REVOKE of a privilege also removes the ones above it, and REVOKE ALL removes the grant. Principals are USER name or GROUP name (a bare name works when it is unambiguous; roles cannot be granted, use a group). A schema grant already covers tables created later, so FUTURE and ALL TABLES IN SCHEMA both create it. Not supported, and refused with a reason: WITH GRANT OPTION, GRANT OPTION FOR, column-level grants and grants on all tables of a catalog. The same rule as the UI decides who may grant (an administrator or the catalog's owner); a grant on a table or schema that does not exist is refused; every statement is audited (SQL_GRANT / SQL_REVOKE). Dropping a table or deleting a catalog removes its grants, so a new table of the same name starts with no access. The default warehouse catalog is open to every user, so use table grants in other catalogs. A table dropped with a SQL DROP TABLE (rather than the explorer's Drop) keeps its grants until they are revoked.
  • Bootstrap admin account: a brand-new, empty warehouse volume seeds no accounts by itself. It reads exactly one admin account from the INIT_ADMIN_USERNAME / INIT_ADMIN_PASSWORD_HASH / INIT_ADMIN_DISPLAY_NAME environment variables (generate the hash with docker exec -it <container> python -m web.auth hash-password, or without a terminal by piping the password: printf '%s\n' "$PW" | docker exec -i <container> python -m web.auth hash-password — a plaintext password is never written to .env or any config file) and refuses to start without one, since there would be no way to log in. This only runs once, the first time the users table is genuinely empty; it never re-applies to, or alters, an already-seeded warehouse. The bootstrap admin (and any user whose password an admin resets) must change that password on first login — enforced server-side on every /api/* request, not just hidden behind a UI modal.
  • OAuth 2.0 / OIDC: Real authorization-code sign-in with PKCE, state and nonce for any standards-compliant OpenID Connect provider (Okta, Entra ID, Keycloak, Google, Auth0, ...). Enable it under Platform Settings → Authentication, register the shown Redirect URI with the provider, and a Sign in with … button appears on the login screen. ID tokens are verified against the provider's keys (issuer, audience, expiry, nonce); the role comes from the configured group claim, refreshed at each login. An existing local or LDAP username, or an account an administrator deactivated or deleted, is never taken over or reactivated by an OIDC login.
  • LDAP / Active Directory: real service-account bind, user search and bind-as-user credential verification (never a cached hash, so a directory password change or lock applies on the next login), group-to-role mapping, and automatic provisioning of a local account (auth_source=ldap) that only that directory can ever authenticate. Sync provisions every not-yet-known directory user, re-resolves every already-known LDAP account's role, and deactivates one locally if its directory entry is gone. An existing local username is always refused, so an LDAP login (or sync) can never take over a local account. Sync group: set sync_group to restrict LDAP access to one directory group — non-members are refused at login, skipped by sync, and deactivated on re-sync if they leave. admin_group, power_user_group and user_group map directory groups to local roles; a sync-group member in none of them gets the Default Fallback Role.
  • Change your own password: user menu → Change password (accounts whose password is kept in the studio's own database only). It needs the current password, and sessions signed in before the change are signed out. Administrators can still reset any password from Users & IAM.
  • Multi-Factor Authentication (MFA): opt-in TOTP (RFC 6238) for any authenticator app. User menu → Two-factor authentication shows a QR code, asks for a first code to confirm, then displays 10 single-use backup codes once. Password sign-ins (local and LDAP) then take two steps; OIDC accounts use their identity provider's own second factor. A code works once, wrong codes are rate-limited (5 failures lock the second factor for 5 minutes), and turning MFA off or regenerating backup codes needs a current code (plus your password for local accounts). Administrators can reset a user's MFA from Users & IAM if a device is lost.
  • Provisioning (SCIM 2.0): Users & IAM → Provisioning (SCIM) (administrators) lets Microsoft Entra ID, Okta or any SCIM 2.0 client create, update, deactivate and delete users and groups automatically, mapped onto local users and groups. The endpoint is /scim/v2 (shown on the tab: give it to the IdP as tenant / base URL).
    • Setup. Turn it on, choose whether provisioned users sign in with OpenID Connect or SAML (their accounts are created for that provider, so its sign-in accepts them), create a token (shown once; the studio keeps only a hash; each token can be revoked and can expire) and paste both into the IdP: Entra ID: Enterprise application → Provisioning → Automatic → Tenant URL and Secret token. Okta: SCIM 2.0 app integration with an HTTP-header bearer token. Map the IdP's user name to userName: it must equal the username people get when they sign in (the OIDC username claim or the SAML username attribute). SCIM answers 403 while it is switched off. If the studio has an IP allowlist, allow the IdP's provisioning addresses.
    • What SCIM can touch. Only accounts and groups that SCIM created. A local account, the administrator, an LDAP account and groups made by hand are invisible to it (404), and a create that collides with one is refused (409): a stolen token can neither take over nor reveal them. Provisioned users show a SCIM badge in the user list.
    • Users. POST/GET/PUT/PATCH/DELETE /Users with the filters IdPs use (eq ne co sw ew pr and or not and parentheses, on userName, externalId, displayName, emails.value, active, name parts, id), startIndex/count paging (max. 200), and the PATCH styles of Entra (Replace, string booleans such as "False", emails[type eq "work"].value) and Okta (no path, a value object). active=false deactivates at once (sessions stop working); DELETE soft-deletes like an administrator's delete and provisioning the same userName again restores the account. A userName cannot be changed (grants and history refer to the account). Attributes this studio does not keep are ignored, not rejected. A sign-in through OIDC/SAML no longer changes a provisioned user's role or name: SCIM is authoritative for them.
    • Roles. A provisioned user gets the default role. Optionally the IdP's roles attribute and a mapping IdP group name → role can raise it (the highest wins). Nothing can exceed the highest role SCIM may grant (default power_user): administrators are only provisioned if an administrator explicitly raises that limit, so a compromised IdP token cannot mint administrators. Roles are recomputed when a user, a group membership or these settings change.
    • Groups. /Groups creates platform groups (source scim) usable everywhere groups are (catalogs, tables, dashboards, policies...). The IdP's displayName is kept and used by filters; the platform name is a sanitised, unique version of it (a clash with a hand-made group gets a suffix; the hand-made group is untouched). Members are managed through PATCH add/remove/replace (members[value eq "id"] too) or PUT. SCIM sees and edits only the members it owns: a member you add by hand stays and is invisible to it. A SCIM group cannot be re-mapped by hand, and its SCIM-owned members cannot be removed by hand (it would be undone by the next sync).
    • Visibility and audit. The tab shows the counts (provisioned, deactivated, groups), the last request and a list of recent requests with the token's name, status and result. Changes are audited as SCIM_USER_CREATE, SCIM_USER_DEACTIVATE, SCIM_USER_DELETE, SCIM_GROUP_*, SCIM_ROLE_CHANGE, SCIM_TOKEN_*, SCIM_CONFIG_UPDATE with the token's name as actor. Not supported: bulk operations, sorting, ETags, password changes (the IdP owns the password), enterprise-extension attributes.
  • Network access (IP allowlist): Users & IAM → Network access (administrators). A per-deployment list of allowed addresses and CIDR ranges (IPv4 and IPv6). Mode Off (default), Monitor (everything is allowed, and every request that would be blocked is recorded: use it to check a new list) or Enforce: a request from an address outside every rule gets 403 before anything else runs, sign-in and SSO callbacks, the UI and /docs included. A change applies at once in every process (a couple of seconds at most).
    • Which address counts. The server trusts only the connecting (TCP) address. Behind a reverse proxy or load balancer, declare its address or range under Trusted proxies (or with TRUSTED_PROXIES in the environment): only then is X-Forwarded-For read, from the right, skipping trusted proxies; the first other address is the client. Whatever a client writes at the left of that header is never believed, a request from an untrusted sender is judged by its own address, and a garbage entry fails closed. Without a declared proxy every user behind it looks like the proxy: the tab warns you when it sees forwarding headers from an untrusted sender. A trusted-proxy range of /0 is refused. The studio must run with uvicorn --no-proxy-headers (the compose file and the Dockerfile do), so nothing rewrites the connecting address first.
    • Always allowed. Loopback without forwarding headers (health checks, docker exec) and the notebook sandbox's own calls to /api/sandbox/*. Loopback with forwarding headers is a reverse proxy on the same host that nobody declared, and is judged like any other address.
    • You cannot lock yourself out by saving. A list that would block the administrator making the change (judged with the new proxy settings) is refused, naming their address; enforcing an empty list and /0 rules are refused too. To declare a proxy in front of the studio, do it while the list is off or monitoring. If everybody is locked out anyway (a proxy address changed, say), set IP_ALLOWLIST_OVERRIDE=off in the studio's environment and restart it: enforcement is suspended without changing the stored list.
    • Visibility. Your connection shows the address the server sees for you, via which proxy, and whether the current rules match it; Check an address tests any address against the saved rules; the activity list shows who was blocked or would have been (kept in memory since the process started, so a flood cannot become database writes). Changes are audited (IP_ALLOWLIST_UPDATE). API: GET/PUT /api/ip-allowlist, POST /api/ip-allowlist/check.
    • Not covered. Rules apply to the whole deployment, not per user or role, and only to the studio's own HTTP port: the compute nodes and other services are not published and stay reachable only on the compose network.
  • Two-factor policy (require MFA): Users & IAM → Two-factor policy (administrators). Tick Require two-factor authentication, choose the roles it applies to and a grace period in days, and save. It covers accounts whose password this studio checks (local and LDAP); accounts that sign in through OIDC or SAML are not asked here, because their identity provider owns that (they are counted separately in the statistics). The grace period starts when the policy is turned on, or when an account is created if that is later; a new account with 0 grace days must enrol at its first sign-in. During the grace period everything works and the user sees a reminder with the days left. After the deadline the user can still sign in but the API refuses everything except enrolling (the same way a forced password change works, enforced on the server, not only in the UI), and the sign-in shows a dialog that cannot be dismissed until two-factor authentication is on. A covered user cannot turn their own two-factor authentication off while the policy is on. Per user, an administrator can Extend the deadline (N days from today) or Exempt the account with a reason (for example a service account); both are audited (MFA_POLICY_UPDATE, MFA_EXEMPT, MFA_EXTEND). Safety: turning the policy on is refused while you are covered and have not enrolled yourself; and if every administrator is ever locked out (lost device, no backup codes), set MFA_POLICY_OVERRIDE=off in the studio's environment and restart it: enforcement is suspended without changing the stored policy.
    Statistics on the same tab: covered accounts, enrolled (and the percentage), in the grace period, overdue (blocked), exempt, SSO accounts (not covered), a breakdown by role, enrolments per week for the last 8 weeks (only for accounts that enrolled after this feature existed), and a list of who needs attention with their state and deadline. API: GET/PUT /api/mfa/policy, GET /api/mfa/stats, POST /api/users/{id}/mfa/exempt|extend (administrators); /api/auth/me and the sign-in response carry mfa_policy for the signed-in user.
  • Column masking: tag-driven masking policies with role, user and group exemptions (see Tags, Masking Policies & Row-Level Security).
  • Row-Level Security (RLS): tag-driven row filter policies (owner, attribute, or custom expression modes), enforced by the same query-rewrite gateway as column masking, with role and user exemptions.

Troubleshooting & Frequently Asked Questions

Q: How do I recover from a corrupted history.db lock?

DataKilnWorks runs SQLite in Write-Ahead Log (WAL) mode. If an unexpected host reboot leaves stale locks, run:
sqlite3 warehouse/.metadata/history.db "PRAGMA integrity_check;"
If errors are reported, execute sqlite3 warehouse/.metadata/history.db ".recover" | sqlite3 history_recovered.db and replace the file.

Q: Can I run DataKilnWorks on Apple Silicon M-series chips?

Yes. The Docker container and underlying DuckDB/Ray binaries natively support ARM64. Execution utilizes Apple Silicon performance cores with full hardware acceleration.
