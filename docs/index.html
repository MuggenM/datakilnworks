DataKilnWorks Lakehouse Platform

The complete reference guide, architecture manual, and developer handbook for DataKilnWorks Studio: an open-source, air-gapped, zero-JVM Data Lakehouse and GenAI Operating System.

1. Overview & Architecture

DataKilnWorks Studio is an enterprise-grade, local and on-premises Data Lakehouse and GenAI Platform. Designed as an uncompromised alternative to cloud-only data ecosystems such as Databricks and Snowflake, DataKilnWorks executes entirely on your hardware—delivering sub-second query latency, sub-20ms distributed worker autoscaling, and complete data sovereignty at $0 cloud operational cost.

Rather than relying on legacy Java Virtual Machine (JVM) clusters or proprietary cloud-locked query engines, DataKilnWorks synthesizes modern, high-performance open technologies into a unified operational canvas:

DuckDB Vectorized C++ Engine
Zero JVM cold starts, in-process SIMD vectorized query execution, sub-10ms analytics, and direct Apache Arrow streaming.
Ray Distributed Actor Pools
Sub-20 millisecond horizontal worker elasticity (0-16 workers), parallel Map-Reduce, and zero-copy Arrow memory via the Plasma Object Store.
Open Delta Lake ACID Storage
Full transaction log integrity (OCC), multi-version concurrency, time-travel queries, and automated compaction/vacuuming.
Unity Catalog Governance
3-level namespace (catalog.schema.table/model/volume), interactive lineage graph, and multi-user home isolation with RBAC.

Core Design Decisions

  • Zero JVM Overhead: By substituting the traditional JVM-heavy Apache Spark cluster with DuckDB and SQLFrame, memory consumption drops by 85%, eliminating garbage collection pauses, Java heap sizing, and slow cluster spin-up delays.
  • True Open Formats: All lakehouse tables are stored in Delta Lake (Parquet + JSON transaction log). There are no proprietary lock-in formats (such as Snowflake micro-partitions), ensuring full external interoperability.
  • Sub-20ms Elasticity: Scaling compute workers in standard cloud platforms takes 2 to 5 minutes. DataKilnWorks leverages Ray Worker Actors to allocate or release worker processes in under 20 milliseconds without restarting containers.
  • Complete Air-Gapped Operation: The platform operates 100% offline with zero external cloud dependencies, making it suitable for defense, healthcare, proprietary IP, and strict data sovereignty environments.

2. Workspace & User Environments

DataKilnWorks enforces enterprise-grade multi-tenancy and workspace isolation modeled directly on Databricks Workspaces. Every authenticated user is automatically allocated a private home environment with strict access boundaries.

Personal Home Directories (Users/<username>/)

Upon user creation or initial login, the workspace subsystem executes init_user_workspace(username) in web/workspace.py:

  • Creates the directory /workspace/notebooks/Users/{username}/.
  • Seeds an interactive personal starter scratchpad: {username}_scratchpad.ipynb.
  • Badges the folder in the UI with a distinct Home tag and house icon.
  • Auto-expands the user's home folder and loads their personal scratchpad notebook upon login.
RBAC Boundary & HTTP 403 Enforcement

Non-admin users (role == 'user' or 'power_user') are strictly isolated. Any attempt to read, write, rename, or delete files in another user's personal directory (e.g. analyst_bob accessing Users/admin/...) is intercepted by can_access_workspace_path() and returns an immediate HTTP 403 Forbidden response.

Notebooks are per user and run inside the studio

There is no separate JupyterLab server. Notebooks are edited and run in the embedded runner, every notebook endpoint requires a valid session, and each user reaches only Users/<their name> and Shared (administrators reach everything). Kernels are per user and notebook, so two users on the same shared notebook never share variables. Users a masking policy applies to run in the notebook sandbox: a separate container with no access to the warehouse files, a separate OS user per person, and no network besides the studio. Their spark, conn and %sql read data through the governance gateway, so it arrives masked. Warehouse files, dbutils and writes to the warehouse are not available there. If the sandbox is not running, they can read and edit notebooks but not run them.

Scratchpad Notebooks & PySpark via SQLFrame

Personal scratchpads support Python, SQL, and PySpark DataFrame code. Through the built-in SQLFrame engine, you can write idiomatic PySpark code that executes directly on DuckDB without starting a JVM:

Users/analyst_bob/analyst_bob_scratchpad.ipynb
Python (PySpark / SQLFrame) 
# Native PySpark DataFrame execution on DuckDB without JVM
from sqlframe.duckdb import SparkSession
from pyspark.sql.functions import col, sum as _sum, avg, to_date

spark = SparkSession.builder.getOrCreate()

# Read directly from an ACID Delta Lake table in Unity Catalog
df = spark.read.table("warehouse.dbo.silver_yellow_tripdata")

# Standard PySpark transformations
summary_df = (
    df.filter(col("trip_distance") > 0)
      .groupBy("payment_type")
      .agg(
          _sum("total_amount").alias("gross_revenue"),
          avg("trip_distance").alias("mean_distance")
      )
      .orderBy(col("gross_revenue").desc())
)

# Output rendering
summary_df.show()

Recents & Activity Tracking

The Recents view (currentView = 'recents') tracks previously opened assets (notebooks, saved queries, and dashboards) per user session. Users can pin critical assets to keep them permanently docked at the top of the sidebar.

3. Catalog & Governance (Unity Catalog)

DataKilnWorks implements full Unity Catalog 3-level namespace compatibility: catalog.schema.table.

Namespace Architecture & Cross-Catalog Joins

Catalogs are stored in separate directories under ./warehouse/catalogs/{catalog_id}/. When querying multiple catalogs, secondary catalogs are mounted into DuckDB via in-memory ATTACH. This enables zero-copy joins across isolated catalogs in a single SQL statement:

Cross-Catalog SQL Join
SQL 
-- Seamless cross-catalog query across warehouse and finance catalogs
SELECT 
    w.employee_id,
    w.employee_name,
    w.department,
    f.salary,
    f.annual_bonus,
    (f.salary + f.annual_bonus) AS total_compensation
FROM warehouse.dbo.silver_employees w
JOIN finance_lake.payroll.salary_records f 
    ON w.employee_id = f.employee_id
WHERE w.active = true
ORDER BY total_compensation DESC;

Delta Lake ACID Logs & Time Travel

Every table mutation writes a forward-compatible JSON commit to the table's _delta_log/. DataKilnWorks supports historical point-in-time reads and rollbacks via standard time-travel syntax:

Delta Lake Time Travel Queries
SQL 
-- Query historical version by commit version number
SELECT * FROM delta_table_version('warehouse.dbo.silver_employees', 2);

-- Compare changes between current snapshot and version 1
SELECT 
    curr.employee_id,
    curr.salary AS current_salary,
    prev.salary AS historical_salary,
    (curr.salary - prev.salary) AS salary_change
FROM warehouse.dbo.silver_employees curr
JOIN delta_table_version('warehouse.dbo.silver_employees', 1) prev
    ON curr.employee_id = prev.employee_id
WHERE curr.salary <> prev.salary;

Delta Shallow Clone

A shallow clone creates a new, independent Delta table from an existing one without copying any data: the clone gets its own transaction log and shares the source's immutable Parquet files. It is instant, costs no extra storage until the clone changes, and is ideal for testing a pipeline change or freezing a table at a point in time. Use Clone on a table in the Catalog explorer, the SQL editor, or the REST API.

Shallow Clone
SQL 
-- Clone the latest version (names must include the schema; a catalog is optional)
CREATE TABLE dbo.silver_employees_test SHALLOW CLONE dbo.silver_employees;

-- Clone an earlier version, by number or by time
CREATE OR REPLACE TABLE dbo.silver_employees_v2 SHALLOW CLONE dbo.silver_employees VERSION AS OF 2;
CREATE TABLE IF NOT EXISTS dbo.silver_employees_1h SHALLOW CLONE dbo.silver_employees TIMESTAMP AS OF '2026-09-24 10:00:00';

-- Across catalogs
CREATE TABLE sandbox.scratch.emp SHALLOW CLONE warehouse.dbo.silver_employees;
  • Hard links, not references: unlike Databricks, where a clone points at the source's files and breaks if the source is vacuumed, the clone here hard-links those files into its own directory. It stays valid if the source is vacuumed, rewritten or dropped, and both readers (delta-rs and DuckDB) see an ordinary table. Source and target must be local catalogs on the same filesystem; a table using deletion vectors or row tracking cannot be cloned.
  • Independent afterwards: writes, deletes, merges and vacuum on either side never affect the other. The clone's first commit (version 0) is an audited CLONE entry that records the source and version.
  • Governance: because a clone shares raw files, a user that a masking or row-filter policy applies to cannot clone at all. For everyone else the clone receives the source's tags (including tags the source inherited from its schema or catalog) before it exists, so masking and row filters keep applying to it. Cloning needs read access to the source catalog and write access to the target catalog.
  • REST: POST /api/table/{schema}/{table}/clone with {"target_table": "...", "target_schema": "...", "target_catalog": "...", "catalog": "...", "version": N, "timestamp": "...", "replace": false, "if_not_exists": false}.

Unity Catalog Volumes

Volumes govern unstructured and semi-structured assets (raw CSVs, PDF documentation, model weights, audio, images). Volumes are addressed via POSIX-compliant paths:

/Volumes/<catalog>/<schema>/<volume_name>/path/to/file.ext

  • Managed Volumes: Storage is hosted and governed directly inside the studio storage layer (./warehouse/volumes/{catalog}/{schema}/{volume}/).
  • External Volumes: Mapped to external storage mounts, NFS, or S3-compatible endpoints.
  • Auto-Loader: a volume can be watched by an Auto-Loader pipeline that ingests new files into a Delta table.
  • Interactive Volume Explorer: Browse directories, upload files via drag-and-drop, and generate presigned download links directly within the UI.

Interactive Data Lineage (22-Node DAG)

The Data Lineage workbench visualizes column-level and table-level lineage. The engine statically parses SQL DDL/DML, dbt schemas, and Delta log operations to construct an interactive Directed Acyclic Graph (DAG) displaying upstream sources and downstream consumers.

Tags, Tag-Driven Masking Policies & Row-Level Security

Tags classify data once; masking policies then protect every column carrying a tag, and row filter policies restrict which rows of every table carrying a tag are visible, wherever they are queried. Tags can be attached to catalogs, schemas, tables and columns, are stored in SQLite (warehouse/.metadata/governance.db), and are inherited downwards: a tag on a schema applies to every table and column beneath it, and a more specific tag overrides the inherited one.

  • Tags: a key with an optional list of allowed values (for example pii = email, phone, name). Manage them in the Governance view (admins) or from the Tags column of the catalog explorer schema tab.
  • Masking policies: bind a tag (and optionally a value) to a mask, with exemptions by role or user. Built-in masks: full, partial, email, null, hash (keyed, so it cannot be reversed by a dictionary attack), date_year, round and a validated custom SQL expression. Each mask states what it does per column type.
  • Row filter policies (row-level security): bind a tag on a catalog/schema/table (never a column, since a row filter restricts the whole table) to a column and a mode: owner (that column must equal the caller's username), attribute (that column must be one of the caller's assigned values for a key, from a built-in membership table you populate under Row Filters → User attributes — nothing assigned means nothing visible, never everything) or a validated custom boolean expression using {col}/{user}/{role}. Several applicable policies on one table combine with AND.
  • Enforcement at query time: a gateway rewrites the SQL of every governed execution path (SQL editor, dashboards, Genie, alerts, scheduled exports, jobs, time travel, Auto-Loader, compute nodes) into SELECT * [REPLACE (...)] FROM table [WHERE predicate AND ...], using scope analysis so that CTEs, joins, subqueries, aliases and SELECT * cannot bypass it. It fails closed: SQL it cannot analyse is refused, and users a policy applies to may only run allow-listed read statements.
  • Suggestions: the classifier proposes tags for untagged columns (emails, phone numbers, names) which an admin accepts in bulk.
  • Preview as user: shows which columns another user sees masked, which tables have a row filter applied for them, and the rewritten SQL, without impersonating them.
  • Tag propagation: when an exempt user runs CREATE TABLE ... AS SELECT over tagged columns, the tags follow onto the new table (computed columns are marked sensitivity=unclassified for review). A copy of a row-filtered table is tagged the same way as its source, so a copy cannot become a full unfiltered leak of the original.
  • Audit & coverage: every tag and policy change is logged, and the coverage view shows which execution paths are governed, how many sensitive columns are still untagged, and which row filter policies match nothing or reference a missing column.
SQL 
-- An analyst with a policy on pii=email sees masked values; an admin (exempt) sees raw values
SELECT name, email FROM warehouse.hr.employees;
-- name | email
-- Ada  | a***@example.com

-- With a row filter policy (attribute mode, column "region") the analyst also sees only their assigned regions:
SELECT name, region FROM warehouse.hr.employees;
-- name | region
-- Ada  | EMEA
Limits of masking and row filtering

Both are enforced in the studio's SQL layer. Notebook kernels run arbitrary Python and cannot be masked or row-filtered, so users either policy applies to run them in the isolated notebook sandbox, where data is only reachable through the governance gateway (see Security Settings). Direct file access to the warehouse is only possible for administrators.

Query History: reuse and fix old queries

Query History is an audit trail: what ran is never rewritten. Opening an entry (Inspect) shows its SQL in an editable working copy. Qualify table names completes every table name to catalog.schema.table by inserting the missing prefix in place (your formatting and comments stay). A name is only completed when it resolves to exactly one table; unknown or ambiguous names are listed and left alone, as are CTE names and table functions. From there use Open in SQL editor or Save as query to keep the corrected version under Saved Queries.

The history is append-only for everyone except administrators: only an admin sees the checkboxes and Delete selected (and Clear History). Every deletion is written to the governance audit log (HISTORY_DELETE / HISTORY_CLEAR: who, how many, which query ids; never the SQL text). Saved queries are not affected.

SQL Warehouses (Dynamic Compute Sizing)

Compute endpoints allow isolating analytical workloads from transformation jobs. Warehouses can be scaled dynamically across T-shirt sizes:

  • 2X-Small: 1 vCPU, 1 GB RAM (Ad-hoc testing, scratchpad exploration)
  • Small: 2 vCPU, 4 GB RAM (General querying)
  • Medium: 4 vCPU, 8 GB RAM (Standard BI & dashboards)
  • Large: 8 vCPU, 16 GB RAM (Complex aggregations & joins)
  • 2X-Large: 16 vCPU, 32 GB RAM (Heavy ETL & compaction jobs)

Auto-suspend and auto-resume are real. A warehouse that has been idle for its Auto-Stop timeout has its compute-node container stopped, releasing its memory (or paused, with WAREHOUSE_SUSPEND_MODE=pause: frozen, instant resume, memory kept). The next query resumes it automatically: the studio starts the container, waits until the worker answers (a few seconds) and runs the query there, and the result reports how long the resume took (warehouse_resumed_ms). Concurrent queries share one resume, a running query is never interrupted, and the idle clock starts when work ends. Start and Stop on the SQL Warehouses page act on the container too (administrators and power users only), and a container stopped by hand is noticed.

  • Docker socket isolation: the studio never holds the Docker socket (that would be root on the host). The container-controller service does, and only offers start / stop / pause / unpause of an allow-list of this project's compute-node services, authenticated with a token on an internal network shared only with the studio. Everything else it refuses with a 404.
  • Rootless Docker: the socket lives at $XDG_RUNTIME_DIR/docker.sock; set DOCKER_SOCKET_PATH in .env (e.g. /run/user/1000/docker.sock).
  • When it is not enforced: without the controller, or for a warehouse whose endpoint is not one of the managed compute nodes, the timeout is only a setting; the page shows not enforced and Start / Stop only change a flag. Tuning: AUTOSUSPEND_INTERVAL_SECONDS (check period, default 30) and WAREHOUSE_RESUME_TIMEOUT (default 60).

5. Data Engineering & Pipelines

Data Ingestion ("Add Data" Wizard)

The Data Ingestion Wizard allows drag-and-drop ingestion of raw files into Delta Lake tables:

  1. Upload: Drop .csv, .tsv, .parquet, or .json files into the upload target.
  2. In-Process Schema Inference: DuckDB samples the file in-process to infer column headers, data types, and nullability without loading the entire file into memory.
  3. Destination Configuration: Pick the target catalog from a dropdown, then type the schema (e.g. bronze) and destination table name. The dropdown lists the local catalogs and every writable S3 mount (marked S3); read-only mounts and mounts that are not Delta stores (e.g. PostgreSQL) are not offered and are refused by the API. For an S3 catalog the table is written to s3://<bucket>/<schema>/<table> with that mount's endpoint and credentials, and append, merge and schema evolution work as they do locally.
  4. File format: a dropdown (CSV, TSV, Parquet, JSON, JSON Lines, NDJSON) sets the file pattern; Custom pattern… accepts any glob such as sensor_*.csv.
  5. Connections (HTTP(S) files, REST APIs, SFTP): the Connections button saves the login for an external server once (administrators create and edit; power users can pick them). The secret (token, password, private key) is stored encrypted, is never shown again and never appears in logs, the audit trail or an API response. A pipeline chooses Connection as its source, picks the connection and adds a path; it can only extend the connection's base URL or folder, so the login can never be sent to another host. Connection sources are polled (an interval or a cron schedule); file events do not apply.
    • HTTP(S) file: the file is loaded when it is new or changed (ETag / Last-Modified, otherwise by its content); an unchanged file is not downloaded again. The format comes from the URL's extension or the server's content type.
    • REST API returning JSON: set the records path (e.g. data.items), optional query parameters and pagination (page number, offset + limit, or a next link in the response). Every poll fetches all pages as one snapshot; an unchanged response is skipped. For an API that returns the current state use Merge (with key columns) or Overwrite; Append would add the records again whenever anything changes.
    • SFTP: password or private-key login. The server's host key fingerprint is pinned in the connection (press Test to see it, compare it with the one your provider publishes, press Pin this) and is checked on every connect: a changed or impersonated server is refused. Files matching the pattern are loaded once each (path + size + modification time); a file still changing (within the settle time, default 10 s) waits for the next poll. Sub-folders are optional.
    Nothing on the remote side is ever changed or deleted. Downloads are capped at 1024 MB (AUTOLOADER_MAX_DOWNLOAD_MB). A corrupt download is quarantined locally and not retried; an unreachable server or refused login sets the pipeline to ERROR and is retried on the next poll.
  6. Write Strategy: Choose between Overwrite (replace table) or Append (add rows).
  7. ACID Materialization: The engine writes Parquet columnar files and commits the transaction into the table's _delta_log/.

Transformations (dbt Core Native Integration)

DataKilnWorks features a native dbt Core runner built directly into the studio. Rather than requiring external dbt Cloud subscriptions or terminal context-switching, users execute dbt workflows inside the UI:

  • Commands: One-click execution of dbt run, dbt test, dbt docs generate, and dbt compile.
  • Live Execution Stream: ANSI-color-decoded stdout and stderr stream live to the browser interface.
  • Model Dependency Graph: Interactive visualization of dbt model dependencies (e.g. stg_trips → fact_taxi_trips).
  • Per-User Run History: Execution logs and test outcomes are archived and scoped per user.
  • The duckrun adapter: the project's profile uses type: duckrun, a dbt adapter built on dbt-duckdb. SQL runs in DuckDB, and table / incremental models are written as real Delta Lake tables into the lakehouse at <warehouse>/<schema>/<model> (schema dbt by default; +schema: marts gives dbt_marts), so they show up in the catalog and SQL editor. view models stay views in dbt_analytics.duckdb. dbt-core, jinja2 and duckrun are pinned in requirements.txt.
  • Closed by default: dbt output is derived from governed tables, so before a run each schema dbt writes to is tagged access=closed and a row policy (dbt output closed by default) denies all rows of closed tables to everyone except admins and power users. Users see the table but no rows until an administrator clicks Open to users on that model (audited; POST /api/dbt/models/{name}/open, /close reverses it). Because the tag sits on the schema, a new model or a new +schema is closed the moment it is created.
  • Opening keeps masking: after every run each output column receives the tags of the source columns it derives from (column lineage is followed through renames, aggregates and CTEs), and the table receives its sources' table-level tags, so masking policies and row filters keep applying to an opened table. Removing a source tag removes the derived tag on the next run. A policy that applies to a role also makes those users governed (sandboxed notebooks, no file functions); set DBT_CLOSED_BY_DEFAULT=false to turn the mechanism off.
  • Editing the configuration: administrators can edit profiles.yml and dbt_project.yml under Project files in the Transformations view. A save is validated first (YAML, the project's profile must exist, dbt parse on a scratch copy, and hooks may only call macros that exist) and refused with dbt's message if it would break dbt, leaving the file untouched. The previous version is kept (last 20 per file, in the warehouse metadata) and can be reloaded, and every save is audited (who, how many lines; never the content). Credentials in plain text are flagged; use {{ env_var('...') }}.
  • Git sync: when GIT_REMOTE_URL (plain http(s), no credentials in it), GIT_TOKEN and optionally GIT_BRANCH (default main) are set, a Git panel appears in Project files (administrators only). Connect turns the project directory into a checkout of the remote branch without overwriting any file (differences show as uncommitted changes). Commit is authored as you and audited; it is refused while a project file holds a plain-text credential. Push never forces. Pull is fast-forward only, refused with uncommitted changes, and checked with dbt parse; if dbt rejects the pulled project the pull is rolled back. Every dbt run records the commit it ran from. The project must be its own repository (DBT_PROJECT_HOST_DIR outside the platform repository); otherwise git sync refuses to act.
  • Git sync of shared notebooks: set NOTEBOOKS_GIT_REMOTE_URL (and NOTEBOOKS_GIT_TOKEN, which falls back to GIT_TOKEN) to get a Git button in the Workspace toolbar (administrators). It works like the dbt panel (connect, commit, fast-forward pull, push, all audited as NB_GIT_*) but only synchronises the Shared folder; private Users/ folders are never sent. Outputs and execution counts are stripped from committed notebooks (your copy keeps them), files over 5 MB are refused, and a pull that brings in a file that is not a valid notebook is rolled back. Use a repository of its own for it.
  • Guided settings: above the text, a small form covers the settings people actually change: where dbt writes (local warehouse or an S3 mount), the schema, threads, and the default materialization per model folder. Apply to the files proposes the change as minimal text edits (comments and everything the form does not know about are untouched); nothing is saved until you press Save, which validates as usual.
  • Where the project lives in production: keep the dbt project in its own git repository, not in the platform's, and set DBT_PROJECT_HOST_DIR in .env to a checkout of it (the default ./dbt_project is for development). An empty directory is seeded once from a starter template; an existing project is never overwritten. The studio does not commit: commit UI edits from your own workflow. Config history and the audit trail are application data in the warehouse metadata, not part of the project repository.
  • Landing tables in an S3 mount: choose an S3 mount in the guided settings and click Apply to the files. Models are then written to s3://<bucket>/<schema>/<model>, which is the layout the mount's catalog reads. The mount's endpoint and keys reach dbt as DKW_MOUNT_<ID>_* environment variables (bucket, endpoint, endpoint URL, key id, secret, region, URL style, SSL), so no secret is written to the file and a rotated key applies automatically. Closed-by-default, opening and masking carry-over behave as for local tables, in the mount's catalog; users additionally need READ on that catalog.
  • Upgrading from the plain dbt-duckdb adapter: the old tables stay behind in schema main of the DuckDB file. A profile that keeps dbt's default schema main would collide with them; the project's on-run-start macro drop_legacy_duckdb_tables then drops only those legacy tables once.

Auto-Loader Pipelines (Volume to Delta)

Auto-Loader pipelines incrementally ingest files that land in a Volume into a Delta table, tracking which files were already loaded so each file is processed once.

  • Formats: CSV, JSON, Parquet and text, with schema inference and schema evolution.
  • Write modes: append or merge on one or more keys (key values are escaped, so odd column names are safe).
  • Rescued data: values that do not fit the schema land in a rescued-data column instead of failing the run.
  • Streaming-style batches: large loads are processed in batches (AUTOLOADER_BATCH_ROWS) with per-run history.
  • Triggers: a poll interval (5 s and up), a cron schedule, on demand, or File events: the pipeline starts as soon as a file is completely written or renamed into the folder (Linux inotify; typically about a second). A file that is still being written is never loaded; hidden, .tmp, .part and non-matching files are ignored, and a burst of files becomes a few runs. A low-frequency safety-net rescan (default every 5 minutes) still runs, because filesystem events can be missed on network drives or while the studio is down, and a catch-up run starts whenever watching starts. If inotify is unavailable the card shows watch unavailable and the pipeline keeps polling. File events and a cron schedule are alternatives.
  • S3 and S3-compatible buckets: set the source to s3://bucket/prefix/ (AWS S3, MinIO, Garage, Ceph, R2, ...) and pick an S3 storage mount (added with Mount in the catalog) for the endpoint and credentials. Each poll lists the prefix and streams new objects straight from the bucket into Delta without downloading them. An object counts as new when its key, size or ETag is new; identical bytes uploaded again are not reloaded. Objects under hidden folders, _quarantine/, .tmp/.part files and non-matching names are ignored. A malformed object is copied under _quarantine/ and deleted from its original key when the credentials allow it. S3 sources use a poll interval (30 seconds or more recommended, since every poll is a list request) or a cron schedule; File events is local-only.
  • Lineage: the source Volume appears as a node in the lineage graph.
  • Governance: ingestion runs as the pipeline owner, and tags propagate to the target table.

Jobs & Pipelines (Local Workflows DAG)

The Jobs & Pipelines engine orchestrates multi-task workflows without requiring external schedulers (such as Apache Airflow or Celery). Supported task types include:

  • SQL Transformation (sql): Vectorized SQL executed directly in DuckDB.
  • Delta Maintenance (optimize): Compaction and bin-packing via OPTIMIZE and vacuuming via VACUUM.
  • Headless Notebook (notebook): Parameterized execution of .ipynb notebooks via Papermill.
  • File Ingestion (ingest): Automated pickup of landing zone files into Delta tables.

7. Platform & System Administration

Ray Distributed Compute Engine

DataKilnWorks incorporates a dynamic Ray Distributed Compute Fabric:

  • Dynamic Actor Pools: DuckDB worker actors are spun up dynamically per warehouse.
  • Sub-20ms Scaling: Scale from 0 to 16 compute workers in milliseconds without container recreation.
  • Plasma Object Store: Workers exchange Apache Arrow RecordBatches via shared memory with zero serialization overhead.
  • Heterogeneous Clusters: Runs across mixed x86_64 and ARM64 nodes (e.g. Apple Silicon M-series, AWS Graviton, and Raspberry Pi 5).

Identity, Authentication & Governance

DataKilnWorks includes a native security stack supporting enterprise authentication protocols:

  • Role-Based Access Control (RBAC): Three built-in roles: admin (full platform governance), power_user (pipeline/model authoring), and user (query execution & reporting).
  • Bootstrap admin account: a brand-new, empty warehouse volume seeds no accounts by itself. It reads exactly one admin account from the INIT_ADMIN_USERNAME / INIT_ADMIN_PASSWORD_HASH / INIT_ADMIN_DISPLAY_NAME environment variables (generate the hash with docker exec -it <container> python -m web.auth hash-password, or without a terminal by piping the password: printf '%s\n' "$PW" | docker exec -i <container> python -m web.auth hash-password — a plaintext password is never written to .env or any config file) and refuses to start without one, since there would be no way to log in. This only runs once, the first time the users table is genuinely empty; it never re-applies to, or alters, an already-seeded warehouse. The bootstrap admin (and any user whose password an admin resets) must change that password on first login — enforced server-side on every /api/* request, not just hidden behind a UI modal.
  • OAuth 2.0 / OIDC: Real authorization-code sign-in with PKCE, state and nonce for any standards-compliant OpenID Connect provider (Okta, Entra ID, Keycloak, Google, Auth0, ...). Enable it under Platform Settings → Authentication, register the shown Redirect URI with the provider, and a Sign in with … button appears on the login screen. ID tokens are verified against the provider's keys (issuer, audience, expiry, nonce); the role comes from the configured group claim, refreshed at each login. An existing local or LDAP username, or an account an administrator deactivated or deleted, is never taken over or reactivated by an OIDC login.
  • LDAP / Active Directory: real service-account bind, user search and bind-as-user credential verification (never a cached hash, so a directory password change or lock applies on the next login), group-to-role mapping, and automatic provisioning of a local account (auth_source=ldap) that only that directory can ever authenticate. Sync provisions every not-yet-known directory user, re-resolves every already-known LDAP account's role, and deactivates one locally if its directory entry is gone. An existing local username is always refused, so an LDAP login (or sync) can never take over a local account. Sync group: set sync_group to restrict LDAP access to one directory group — non-members are refused at login, skipped by sync, and deactivated on re-sync if they leave. admin_group, power_user_group and user_group map directory groups to local roles; a sync-group member in none of them gets the Default Fallback Role.
  • Change your own password: user menu → Change password (accounts whose password is kept in the studio's own database only). It needs the current password, and sessions signed in before the change are signed out. Administrators can still reset any password from Users & IAM.
  • Multi-Factor Authentication (MFA): opt-in TOTP (RFC 6238) for any authenticator app. User menu → Two-factor authentication shows a QR code, asks for a first code to confirm, then displays 10 single-use backup codes once. Password sign-ins (local and LDAP) then take two steps; OIDC accounts use their identity provider's own second factor. A code works once, wrong codes are rate-limited (5 failures lock the second factor for 5 minutes), and turning MFA off or regenerating backup codes needs a current code (plus your password for local accounts). Administrators can reset a user's MFA from Users & IAM if a device is lost. There is no organisation-wide “require MFA” policy yet.
  • Column masking: tag-driven masking policies with role and user exemptions (see Tags, Masking Policies & Row-Level Security).
  • Row-Level Security (RLS): tag-driven row filter policies (owner, attribute, or custom expression modes), enforced by the same query-rewrite gateway as column masking, with role and user exemptions.

Masking is enforced by default. An invalid or expired session is never treated as an administrator. Requests with no credentials at all run as the local admin in single-user mode; set GOVERNANCE_REQUIRE_AUTH=true for any shared deployment.

  • File sandbox: non-admin users cannot read arbitrary files (such as the warehouse's Delta files or metadata) through SQL file functions.

When an upgrade adds a Python dependency (recently boto3 for S3 sources and paramiko for SFTP connections) the image must be rebuilt: docker compose build, then docker compose up -d. Edits to web/ alone need no rebuild.

Troubleshooting & Frequently Asked Questions

Q: How do I recover from a corrupted history.db lock?

DataKilnWorks runs SQLite in Write-Ahead Log (WAL) mode. If an unexpected host reboot leaves stale locks, run:
sqlite3 warehouse/.metadata/history.db "PRAGMA integrity_check;"
If errors are reported, execute sqlite3 warehouse/.metadata/history.db ".recover" | sqlite3 history_recovered.db and replace the file.

Q: Can I run DataKilnWorks on Apple Silicon M-series chips?

Yes. The Docker container and underlying DuckDB/Ray binaries natively support ARM64. Execution utilizes Apple Silicon performance cores with full hardware acceleration.
